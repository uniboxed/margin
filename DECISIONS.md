## Environment

- **Playwright/Chromium:** Chromium is preinstalled in the cloud session (`/opt/pw-browsers`, Playwright 1.63.0), so E2E tests run; nothing is downloaded. `package.json` pins `playwright@1.63.0` as the only dev dependency. Tests load it through `createRequire`, so either a local `npm install` or the global copy works.
- **E2E runner:** E2E tests use `node --test` plus the `playwright` library instead of `@playwright/test`, so there's a single runner and no second dependency.
- **Closed shadow roots in tests:** page JS and Playwright locators can't see into a closed shadow root. The tests use the DevTools protocol (`DOM.getDocument` with `pierce: true` → `Runtime.callFunctionOn`) to inspect and click inside it. Production code keeps `mode: 'closed'`.

## M1 — Skeleton

- **Background as a classic service worker** (originally a module worker; changed after M7, see below).
- **`package.json` has `"type": "module"`** so the `node --test` files can use `import`.
- **Shadow host** is a custom element `<margin-sidebar-host>` appended to `<html>` (`<body>` doesn't exist at `document_start`). Its inline styles use `!important` and `all: initial` so site CSS can't move it, and it has zero size so it never blocks clicks.
- **Toggle-sidebar command** suggests `Alt+S` (Option+S). Whether Safari honors it is a manual check.
- **Icons** are generated by `scripts/make-icons.js` (no image dependencies).

## M2 — Sidebar overlay

- **Tab snapshot in storage.** Content scripts have no `tabs` API, so the background mirrors open tabs into `storage.local.tabs` (`{id, windowId, index, title, url, favIconUrl, active, lastActive}`) and the sidebar renders from storage alone. This is an addition to the SPEC data model. `onUpdated` only writes on title/url/favicon changes or load complete, not on every status tick.
- **Serialized mutations.** All background writes go through one promise queue (`mutate`) with an in-memory cache that's rebuilt from storage whenever the worker wakes, and only changed keys are written. Content scripts never write storage; they message the background.
- **Fresh-session detection.** After a browser restart, tab and window ids are reused with different meanings. If `storage.session` exists (it's cleared on restart), an empty one means "fresh: rebuild `tabSpace` from pins by URL." Otherwise `runtime.onStartup` triggers the rebuild. On a plain worker wake, assignments are kept and only reconciled.
- **Pins are URL-based** (normalized: no fragment, no bare trailing slash). A tab whose URL matches a pin in its space shows as that pin, not in the tab list. Navigating a pinned tab elsewhere turns it back into a normal tab. Arc keeps the tab↔pin link, but SPEC chose URL pins.
- **Messages:** the SPEC set plus `hello` (returns the sender's tab/window id), `openPin`, `updateSettings`, and (later) `deleteSpace`, `restoreArchive`. Handlers reply via `sendResponse` + `return true`, which both Chrome and Safari support.
- **CSS in the shadow root** is fetched from the web-accessible `content/sidebar.css` and applied as a constructable stylesheet, which is exempt from the page's CSP. A `<style>` element is the fallback. The new-tab page links the same file.
- **Hover logic** is one capture-phase `mousemove` listener on `document`: x ≤ 6px opens, x > 260px starts the 300ms hide timer, moving back inside cancels it. There's no edge hit-zone element, so the page's own left 6px stays clickable.
- **Shortcut toggle** opens the sidebar until toggled again, Esc, or a click on the page. "Keep open" in the footer sets the global `sidebarPinnedOpen`.
- **Theme:** the page's computed `color-scheme` (if `dark`), else the luminance of the body/html background, else the OS `prefers-color-scheme`.
- **"+ New tab"** calls `tabs.create` without a URL, so the browser's new-tab setting (Margin) decides the page.
- **Host debug attribute:** the host carries `data-open="true|false"` so state is visible in Web Inspector. It reveals nothing beyond the sidebar being open.

## M3 — New-tab page

- **Launcher navigates the new-tab tab itself** (`tabs.update`) instead of opening another tab.
- **URL vs. search** (`shared/search.js`, unit tested): explicit schemes pass through, `localhost`/IPs get `http://`, `name.tld[/…]` without spaces gets `https://`, and everything else is searched. `node.js` alone counts as a URL, like most browsers.
- **Search engine setting** is a URL template with `%s` (`settings.searchEngine`). The new-tab "Settings" disclosure offers DuckDuckGo (default), Google, Bing, Ecosia, and Startpage. A stored template that's not in the list shows as "Custom."
- **Pin tiles** focus an open tab with that URL, otherwise navigate the new-tab tab to it.
- **No palette auto-open on the new tab.** SPEC's layout comment mentions it, but the launcher field already does that job. The palette is available on the new tab through its shortcut (M5).

## M4 — Spaces and pins

- **Editing spaces:** right-click (or double-click) a space chip opens an inline editor in the sidebar with name, emoji, an 8-color palette, Save/Cancel, and Delete. "+" creates a space, switches this window to it, and opens the editor. The emoji is free text (paste or use the macOS emoji picker, Ctrl+⌘+Space).
- **Delete** takes two clicks ("Delete" → "Really delete?") instead of a `confirm()` dialog, which would block the page. The last space can't be deleted. Its tabs, pins, archive entries, and windows move to the first remaining space, and pins whose URL is already pinned there collapse into one.
- **Drag and drop** uses HTML5 DnD from a tab row onto a chip. The tab id is tracked in memory as well as in `dataTransfer`, because some browsers hide custom types during `dragover`.
- **Auto-hide is suspended** while the editor is open or a drag is in progress.
- **Our keystrokes stay in the sidebar:** key events stop propagating at the sidebar root, so typing a space name doesn't trigger the site's own shortcuts (e.g. GitHub's `/` or `s`). Page listeners in the capture phase still see them; that can't be prevented from a content script.
- **Archive helpers** (`archiveTab`, cap 200, one entry per URL, newest first) landed here so the cap is unit tested with the rest of the model. M6 uses them.

## M5 — Command palette

- **Default shortcut stays Option+K (`Alt+KeyK`), unverified.** I can't check whether Safari or macOS swallows it. Matching uses `KeyboardEvent.code`, so Option+K is recognized even though macOS types `˚`, and the physical key works on any keyboard layout. If it's swallowed in Safari, change it in new tab → Settings (any modifier + letter/digit/punctuation), then update the default in `state/model.js` and record it here. Manual check in TESTING.md.
- **Two triggers, de-duplicated:** a capture-phase `keydown` listener in the content script (and on the new-tab page), plus a `commands` entry `open-palette` (suggested Alt+K). The background forwards the command to the tab's content script, or as a runtime message to our new-tab page. Toggles within 200ms collapse, so both firing for one press doesn't open and immediately close it.
- **The shortcut works inside text fields too.** It's intercepted everywhere, which means a user can't type `˚` with the default key on websites. Changing the shortcut avoids that.
- **Ranking** (`shared/search.js`, unit tested): every space-separated token must fuzzy-match the title or URL. Substrings beat subsequences, prefixes and word starts get bonuses, and current-space tabs get the biggest boost, then current-space pins, actions, other-space tabs and pins, then archive. With an empty query: current-space tabs by recency, then actions; the archive is hidden until you type. The current tab isn't suggested.
- **"Open URL / Search for …"** comes first when the text is a URL and last when it's a search, so Enter on a fuzzy match isn't hijacked. From a web page it opens a new tab (Arc's ⌘T behavior); on the new-tab page it navigates in place.
- **Actions:** New tab, Pin current tab (only on unpinned web pages), Toggle sidebar (not on the new-tab page, where it's always open), and one "Switch to space …" per other space.
- **`content/palette.css`** was added next to `sidebar.css` (not in SPEC's layout) so each shadow root only loads its own styles.
- **Keys:** ↑/↓ (or Ctrl+N/Ctrl+P) wrap around, Enter runs, Esc or a click on the backdrop closes, and focus returns to where it was.

## M6 — Auto-archive

- **Both schedulers are implemented; which one runs depends on the browser.** If `browser.alarms` exists, a 15-minute alarm (`margin-archive`) runs the check (verified in Chromium). Otherwise the check runs on tab activation, throttled to once every 5 minutes. Either way, it also runs every time the background wakes. The background logs which path it took (`[margin] auto-archive via …`). Which one Safari uses is a manual check. `alarms` was added to `permissions`.
- **Staleness clock:** `tabs[id].lastActive`, stamped when a tab gains or loses focus. Safari's `tab.lastAccessed` is used only as a seed when present. When a tab is first seen with no history, the clock starts then, so a restart never archives everything at once. On a fresh browser session all clocks restart.
- **Never auto-archived:** the active tab of each window, tabs pinned in their own space (a pin in another space doesn't protect it), and non-web pages (our new tab, `about:`, Safari internal pages).
- **`archiveAfterHours: 0` disables auto-archive.** It's editable on the new tab under Settings.
- **Closing a tab from Margin's × archives it**, like Arc. Tabs closed with ⌘W or by closing a window are **not** archived, deliberately: `tabs.onRemoved` can't tell a deliberate close from a window close or quit, and archiving every one of those would flood the archive.
- **Restore** removes the entry, reopens the URL in its original space, and switches the window to that space so the tab is visible. That space falls back to the first space if it was deleted. From the new tab it navigates in place; from the palette it opens a new tab.
- **Debug hook:** `margin.archiveNow()` in the background's console (Web Inspector) runs the check immediately. E2E uses it with a 1-second threshold.

## Arc frame, push when kept open, faster first render (2026-10-25)

- **Late sidebar fixed.** The sidebar used to wait for the background's `hello` reply before drawing, because it didn't know its window. In Safari the background is usually unloaded, so the sidebar showed up only after a wake-up, often after the page finished loading. It now draws straight from storage using `view.guessWindow()` (single window → that one; else a tab with this URL, active and most recent first) and corrects itself when `hello` answers. The panel is also hidden until its CSS is applied, so it never flashes unstyled.
- **Arc-style frame.** The sidebar is now opaque and shares one color with a frame around the page: an 8px margin top, right and bottom with 10px rounded page corners, tinted 14% toward the active space's color. The frame is a `pointer-events: none` overlay (a rounded "hole" with a huge box-shadow), so the page stays fully clickable. It shows only while the sidebar is open (Tirth's choice), and the new-tab page uses the same layout.
- **Push when kept open (Tirth's choice, overriding SPEC's original "never push").** With `sidebarPinnedOpen`, the content script adopts a stylesheet on the document: `@media screen { html { margin-left: 260px; margin-right: 8px; width: auto; overflow-x: hidden } }`. It's a constructable sheet, not page markup or an inline style. A `<style>` element is the fallback, and it isn't applied to non-HTML documents. It's removed when "Keep open" turns off, and print is unaffected. Top and bottom aren't pushed (the frame overlays 8px there), because pushing vertically adds an outer scrollbar on full-height app layouts like Gmail and Teams. Known breakage: `position: fixed` elements don't move, so left-anchored fixed headers stay partly under the sidebar; `100vw` elements are clipped on the right; viewport-centered modals sit off-center; sites keep their media queries for the full window width. Pages that replace `document.adoptedStyleSheets` wholesale would drop the push until the next state change.

## Sidebar instantly on page load (2026-10-25)

- **Cause:** with "Keep open", the sidebar showed up only after the page finished loading in Safari. Waiting for the background was fixed earlier. The remaining wait was the stylesheet: the content script `fetch()`ed `content/sidebar.css` and kept the panel hidden until it arrived, and in Safari that request likely queues behind the page's own resources. On top of that, the docked sidebar slid in (160ms) on every navigation.
- **Fix:** `content/*.css` stay the source of truth. `scripts/build-styles.js` (`npm run styles`) bundles them into `content/styles.js`, which loads as a content script before the UI and is applied synchronously, so the sidebar is styled from its first frame. A unit test fails if `styles.js` is stale, and another fails if a content script `fetch`es. With no stylesheets fetched by pages, `web_accessible_resources` was removed, so web pages can no longer probe for Margin's files.
- **No animation on first render:** an `instant` class suppresses transitions until two frames after the first render, so a kept-open sidebar is simply there. Hover still animates.
- **The only remaining wait** is one `storage.local.get` (needed to know the spaces, tabs and the "Keep open" setting). Each page logs one `console.debug` line after load (debug level since 2026-10-25, so it's hidden unless the console shows Debug messages): `[margin] timing (ms) injected=… storage=… rendered=… | page DOMContentLoaded=… load=…`, all in ms since navigation start. A late `injected` means Safari ran the content script late; a late `storage` means the `storage.local` read was slow. In Chromium, `rendered` is about 20–45ms against a 1,500ms load.

## First-paint placeholder for "Keep open" (2026-10-25)

- **Measured in Safari (Tirth, google.com):** `injected=176–266 rendered=190–294 | DOMContentLoaded=511–544 load=945–1145`. Margin renders 15–30ms after Safari runs its content script, but Safari runs `document_start` content scripts about 200ms after navigation start, after fast pages have already painted. No content-script change can beat that.
- **Fix:** while `sidebarPinnedOpen` is on, the background registers `content/docked.css` with `scripting.registerContentScripts` (id `margin-docked`, `document_start`) and unregisters it when "Keep open" turns off. It re-syncs on every `settings` change and on wake. Registered CSS is applied before first paint, ahead of content scripts. It pushes `html` (same geometry as the JS push) and paints the docked sidebar and frame background with a single `html::after`: a fixed rounded "hole" with a 100vmax box-shadow, `pointer-events: none`, z-index one below Margin's host. The real sidebar and frame render on top moments later. The placeholder uses the default space tint, light or dark by `prefers-color-scheme`.
- **Switching it off per page:** if a page with the placeholder isn't docked (Keep open turned off, or the setting changed mid-load), `sidebar.js` sets `data-margin-docked="off"` on `<html>`, which the placeholder's selectors exclude. This is the only attribute Margin ever sets on a page's own elements, and only when the placeholder is present.
- **Feature-detected:** the `scripting` permission was added. Without `scripting.registerContentScripts`, the sidebar appears when the content script runs, as before. Known cost: a site with its own `html::after` loses it while docked.

## One highlighted tab per window (2026-10-25)

- **Bug (seen in Safari):** several tabs highlighted at once after opening pages in a row. Cause: `upsertTab` copied `active` from every `tabs.onUpdated` event. Safari can deliver an update for a page that finished loading after the user switched away, still saying `active: true`, which re-highlighted it. Also, a newly created focused tab didn't clear the old highlight unless Safari also sent `onActivated`.
- **Fix in the model:** for known tabs, `active` is now owned by `activateTab()` (exactly one per window), plus the `tabs.query` resync. Updates no longer change it. A new tab that arrives focused activates itself and clears the rest of its window. `activateTab` falls back to the tab's own window when the event has no `windowId`. Unit tests cover the late update, ⌘T without `onActivated`, and activation before creation.
- **Fix in the view:** `view.sidebar(state, windowId, currentTabId)` highlights the tab the sidebar is drawn in (the page being looked at is by definition active). So even a briefly stale snapshot can't highlight the wrong row on the visible page. The new tab passes its own id.

## Safari's own edge sidebar (2026-10-25)

- Safari reveals its own sidebar when the cursor rests at the left edge of a **full-screen** window. It has no setting for this, and extensions can't affect Safari's UI. Mitigations: README recommends Window → Fill instead of full screen, or Keep open. `view.revealZone()` widens Margin's reveal zone from 10px to 24px when the window covers the whole screen (`outerWidth/outerHeight >= screen`), so Margin opens before the cursor reaches the edge. In normal windows it stays 10px to avoid accidental opens near pages' left-edge controls.

## Experiment: sidebar as its own window (2026-10-25)

- **Why:** an in-page sidebar can't exist before Safari paints a new page (the blank moment on navigation), on Safari's own pages, or on PDFs. Safari has no `sidePanel` or `sidebar_action` (checked October 2026), so the only extension-only way to keep a sidebar on screen is a separate window. Tirth chose to try it as an opt-in experiment before considering a native companion app (still out of scope).
- **How:** `setDock {on}` (new tab → Settings checkbox, the palette "Dock sidebar as its own window", or "Undock" in the dock window). On, the background opens `dock/dock.html` as a `type: 'popup'` window, 260px wide, at the left edge of the last-focused normal window, and shrinks that window by 260px. `shared/dock.js` computes the geometry (unit tested). The window must be at least 740px wide. `state.dock` stores `{dockWindowId, targetWindowId, original, requested, actual}`. The dock page renders the normal sidebar for the target window, so clicks act on it. Since Safari has no window-moved event, the dock page polls the target every 500ms and re-docks (`followLayout`, 2px slack), reporting the result via `dockReport`. Off (or when either window closes) gives the target its 260px back. Turning it on also turns "Keep open" off. In the target window, the in-page sidebar and the new tab's built-in sidebar step aside. The dock page's own tab is kept out of the tab list, palette, and archive.
- **What the experiment measures:** whether Safari honors `left/top/width/height` for extension-created popup windows and for resizing a normal window, and what `type` it reports. The dock window shows "✓ Placed as asked / ✗ Not placed as asked" and "follows ✓/✗", with the exact numbers on hover. The background logs `[margin] dock …`. A refused resize is recorded (`actual.targetError`) instead of failing the dock.
- **Known limits even if Safari cooperates:** a separate window with its own title bar, up to 0.5s lag when the Safari window moves, full screen doesn't work (macOS gives each window its own Space), and one dock per profile next to one window.
- **Chromium notes:** headless Chromium validates window bounds against an 800×600 virtual display, and Playwright resizes newly opened pages to its default viewport. So E2E sets sizes after opening pages, and the dock's initial placement is corrected by the follow loop there. The E2E checks the requested layout, the popup type, following, and undocking.

### Dock experiment: first Safari result (2026-10-25)

- **From Tirth's screen recording:** Safari opens the dock as a narrow window, about 260pt, with traffic lights and a compact title bar, at the screen's left edge. The Safari window was resized to sit right of it. So **Safari does honor extension window positions and sizes**, close enough to look right. The status said "✗ Not placed as asked" because Safari's reported coordinates are offset from where it draws windows (the dock was asked for -34pt and macOS kept it at 0).
- **Bug: the dock jumped off-screen and back about twice a second.** The follow loop re-requested the absolute "ideal" position (`target.left - 260`) on every tick. With Safari's offset coordinates that position was off-screen; macOS put the window back, and the next tick moved it again. Fix: `followLayout(prev, target, dock)` now follows **relatively**. It moves the dock only when the target window itself moved or resized since the last tick, by the same delta, from the dock's real position, clamped to the screen's available area. It never re-requests a spot just because the dock isn't exactly where the math says. Unit tests cover the offset case; E2E checks the dock stays still while idle.
- **Tests:** Playwright's default viewport resized every new window, including the dock popup, to 1280×720. `launch()` now passes `viewport: null`, so tests use real window sizes, and Chromium places both windows exactly as asked.
- **Dropped (Tirth, 2026-10-25).** In Safari, the dock window visibly lagged and flickered when the Safari window was dragged: Safari gives extensions no window-moved event, so the dock can only catch up after polling. It also can't exist in full screen, where macOS gives each window its own Space. Both are inherent to a separate window, so the experiment was removed entirely (code, tests, settings switch, palette action). The in-page sidebar remains the only sidebar. The remaining way to a truly persistent sidebar is a native companion app, which is still out of scope. Leftover `dock` and `settings.dockWindow` values from the experiment in `storage.local` are ignored.

## Tab and space shortcuts (2026-10-25)

- **⌘⌥↓ / ⌘⌥↑:** next/previous tab in the order the sidebar shows them: open pinned tabs, then the space's tabs (`view.cycleTab`). Wraps at both ends. From a tab that isn't listed (e.g. one from another space), ↓ goes to the first and ↑ to the last. Holding the keys repeats.
- **⌘⌥→ / ⌘⌥←:** next/previous space for this window (`view.cycleSpace`), wrapping. As SPEC defines spaces, this changes only what the sidebar shows; the current page stays. In auto-hide mode the sidebar peeks open for 1.2s so the new space is visible. Hovering or toggling during the peek keeps it open. Held keys don't repeat, so you don't fly through spaces.
- **Handled** by one capture-phase `keydown` listener (`shortcuts.installNavigation`) in the content script and on the new-tab page. It calls `preventDefault` and `stopImmediatePropagation`, so sites don't get the arrow key. Like Arc, Margin takes these keys on every site, including in text fields. That shadows site shortcuts that use the same keys, e.g. multi-cursor ⌘⌥↑/↓ in web code editors. They're fixed (not a setting) for now. There's no `commands` fallback: Chrome only allows four suggested command keys, and two are already used.
- **Needs a Safari check:** whether Safari or macOS reserves any of these combos before the page sees them (same as the Option+K check).

## Site icons without favIconUrl (2026-10-25)

- **Problem:** Safari leaves `tab.favIconUrl` empty for every tab, so the sidebar only showed letters.
- **Approach (Tirth asked for real icons):** each page's content script picks its best icon link (`view.pickIconHref`: SVG or ~16–64px `rel=icon` first, then any icon, then apple-touch-icon, else `/favicon.ico`) and sends `pageIcon {href}`. The background fetches it once per site (origin): `credentials: 'omit'`, 6s timeout, ≤512KB. It checks the bytes really are an image (`icons.sniffType`, which rejects e.g. HTML error pages served as 200) and shrinks raster icons to 32×32 PNG with `createImageBitmap` + `OffscreenCanvas` (about 1–2KB). Where that isn't possible (SVG, or a format the worker can't decode) it keeps the original if ≤24KB. Then `state.favicons[origin] = { data: 'data:…', href, at }` (`rememberFavicon`, newest 150 sites). Results are re-checked after 7 days; failures aren't retried until the background restarts. If the page's icon fails, `/favicon.ico` is tried.
- **Rendering:** `view.iconFor(state, item)` uses the browser's icon if any (Chrome), else the stored data: URL for that site. It's used by sidebar rows, pins (open or closed), the palette, new-tab tiles and the archive. Showing a stored icon makes no network request. If a page's CSP blocks `data:` images in our shadow root, the `<img>` errors and the letter avatar shows.
- **Safety:** the page chooses the URL, and the background can fetch what pages can't. So icons on another host must be https and not on a local or private network (`iconUrlAllowed`). Same-host icons are always allowed. No cookies are sent.
- **SPEC change:** the "no third-party requests" rule stays; fetching the visited site's own icon is the one request Margin makes (SPEC updated).
- **Needs a Safari check:** whether the background's `fetch` reaches sites under Safari's website-access permission, and whether Safari's worker supports `OffscreenCanvas` (without it, icons are stored unshrunk up to 24KB).

## Reliable navigation shortcuts (2026-10-25)

- **Reported:** the shortcuts were laggy and only sometimes worked (mostly not in Safari). Causes found in the code:
  1. **Overlapping presses:** each press was handled independently, so two quick presses could read the same "current tab" and move once. Reproduced: three back-to-back presses failed with the old handling.
  2. **Focus stealing:** every switch also called `windows.update({ focused: true })` on the already-focused window, which can pull keyboard focus out of the page in Safari, so the next press never reached Margin.
  3. **Lost presses:** the page-key path only works once the new page has focus and Margin's script has loaded (~180–270ms after navigation in Safari, longer for tabs Safari reloads). Presses in that gap go nowhere. That's inherent to listening in the page.
- **Fix 1, manifest `commands` (the main one).** WebKit's source (`WebExtension.cpp`, `WebExtensionCommandCocoa.mm`) shows Safari parses `suggested_key` (`Command`/`Ctrl` = ⌘, `Alt` = ⌥, `MacCtrl` = ⌃; up to 4 shortcut commands), skips only the invalid command rather than the whole extension, and matches the key press in the app (`matchesEvent`), independent of page focus and content scripts. It ignores key repeats. ⌘⌥ can't be used because Chrome refuses `Command+Alt`/`Ctrl+Alt` in any platform entry (including `ios`) and then fails to load the whole extension, verified by bisecting. `MacCtrl+Command` loads in both. So the four commands are **⌃⌘ + arrows** (`Alt+Shift+arrows` as the non-Mac default), and the Settings defaults match: next/previous tab ⌃⌘↓/↑, next/previous space ⌃⌘→/←.
- **Fix 2, background `navigate`.** Commands and the page listener (still there for key repeat and custom shortcuts) both land in one function:
  - **Duplicates:** a press arriving through both paths within 150ms counts once.
  - **Serialized:** presses run one at a time.
  - **Chained:** each tab step continues from the tab the previous step chose (for 1.5s), else the window's real active tab. A manual tab switch clears the chain.
  - **Instant highlight:** activation is recorded immediately.
  - **No re-focusing:** `focusTab` only focuses a window that isn't already focused.
- **Custom shortcuts** recorded in Settings work through the page listener only. Manifest keys are fixed, and Safari has no UI to change them.

## Per-browser builds (2026-10-25)

- **Why:** Safari can bind ⌥⌘↓/↑ as extension commands, but the same manifest makes Chrome refuse to load the extension. One manifest can't serve both, so each browser gets its own build.
- **Layout:** `extension/` stays the single shared source. `platform/<browser>/manifest.json` holds only the manifest keys that differ (today: `commands`). `scripts/build.js` (`npm run build`) copies `extension/` to `dist/<browser>/`, merges the overrides into the manifest, and stamps `shared/platform.js` with the target. Forked per-browser copies of the code were rejected: every fix would have to land twice, and the two would drift.
- **Behavior differences** live in the two profiles in `shared/platform.js`, not in scattered browser checks:
  - **Safari:** tabs ⌥⌘↓/↑, spaces ⌃⌘→/← (Safari keeps ⌘⌥←/→), fetches site icons (no `favIconUrl`).
  - **Chrome:** all four on ⌃⌘ + arrows, no icon fetching (Chrome provides `favIconUrl`, so Margin makes no extra requests there).
- **`dist/` is committed** so the Mac needs no Node to load it. A unit test rebuilds into a temp folder and fails if `dist/` differs; others check each manifest's commands against Safari's parsing rules (and Chrome's ⌘⌥ refusal) and against its profile's default shortcuts.
- **Unbuilt `extension/`** still loads in both browsers (Chrome manifest; the profile is detected from the `safari-web-extension:` URL scheme), but in Safari only the page listener knows ⌥⌘↓/↑ there. Load `dist/safari/` in Safari.
- **Tests:** E2E loads `dist/chrome/`. Favicon tests, and a check that ⌥⌘↓ switches tabs, use a Safari-profile build with Chrome's manifest, since Chromium can't load the Safari manifest. Whether Safari delivers the ⌥⌘↓/↑ commands is a manual check (TESTING.md).
- **Existing installs:** settings saved by an older version keep ⌃⌘↓/↑ for the page listener (the manifest's ⌥⌘↓/↑ still works). Settings → Reset shortcuts switches to the new defaults.

## Tab right-click menu; blocking Safari's swipe and pinch (2026-10-25)

- **Tab menu:** right-click (or ⌃-click) a tab in the sidebar for Pin Tab, Move to <space> (one item per other space), Close Tab; on a pin, Unpin (and Close Tab if it's open). It replaces the 📌 hover button (Tirth asked for a menu instead). Left click still activates the tab. macOS-style: nothing highlighted until hover or ↓/↑; Return/click picks; Esc, a press anywhere else, or the window losing focus closes it. The sidebar doesn't auto-hide while it's open. Same on web pages and the new-tab page (shared/ui.js).
- **Gestures (Safari builds, setting `blockGestures`, default on):** extensions can't change Safari's gesture settings, but WebKit's source shows both gestures defer to the page first:
  - **Swipe back/forward** (`ViewGestureController::PendingSwipeTracker`): starts only from a horizontal scroll the page didn't handle, while the page is at its edge. A page with a wheel listener is asked first, and a cancelled event counts as handled. `overscroll-behavior` isn't consulted. So `shared/gestures.js` cancels mostly-horizontal wheel events that nothing under the pointer can scroll that way (checked up the composed path, including the page itself, RTL-aware). Anything that can scroll sideways still does.
  - **Pinch for all tabs** (`WebViewImpl::magnifyWithEvent` → `gestureEventWasNotHandledByWebCore`): each pinch event goes to the page first and reaches Safari only if not handled. `gesturechange` with `scale < 1` (pinching in) at normal zoom (`visualViewport.scale` ≈ 1) is cancelled. Zooming in, and back out while zoomed, still work.
  - **Costs and limits:** a non-passive wheel listener on every page. WebKit checks the page only at the start of each scroll gesture, which is fine; Chrome would route every wheel event through the main thread, so the Chrome build doesn't install it. Frames other than the top page get their own events (Margin runs only in the top frame). A gesture that starts vertical and turns sideways can still swipe.
  - **Tests:** E2E (Chromium, Safari profile) with real wheel events: sideways blocked, vertical untouched, a sideways-scrollable box still scrolls and is blocked only at its edge, and the setting turns it off. The pinch logic is unit-tested with a stand-in window, because a pinch event made in the test page can't carry `scale` into the extension's script context. Whether Safari honors this is a manual check (TESTING.md).
- **Update (reported: swipe blocked, pinch still opened all tabs):** cancelling only the pinch-in `gesturechange` events wasn't enough. Whether a page "handled" a pinch is decided in `EventHandler::handleGestureEvent`, which isn't in WebKit's open-source tree (Apple's internal additions), so Safari's exact rule can't be read. Most likely Safari starts the overview from the unhandled `gesturestart`. Now, at normal zoom, Margin cancels `gesturestart`, every pinch-in update, and `gestureend` unless part of the pinch zoomed in (those updates still go to Safari). A page that's already zoomed in keeps all its pinch gestures. Pinch-in reported as ⌃+wheel is cancelled too. Trade-off: if Safari also needs the start to zoom, pinching out to zoom in from normal zoom stops working (⌘+ still zooms). Manual check in TESTING.md.

## Vertical trackpad gestures: no bounce, Margin's pull-to-refresh, sidebar scroll (2026-10-25)

- **Asked:** no rubber-band past the page's top/bottom (the dark gap at the end of a page); scrolling over the sidebar mustn't scroll the page (the sidebar scrolls only when it has more than fits); replace Safari's pull-to-refresh (macOS spinner) with Margin's own.
- **Bounce, from WebKit's source:** the page's rubber-band on a side is allowed only if the page's `overscroll-behavior` allows it (`ScrollingTreeScrollingNode` → `overscrollBehaviorAllowsVerticalRubberBand`). For the page itself WebKit reads it from `<html>` (`LocalFrameView::verticalOverscrollBehavior`). So the gesture guard adds `:root { overscroll-behavior-y: none !important }` as an adopted stylesheet (never page markup), live with the `blockGestures` setting (re-synced on each render). Horizontal is left alone (the swipe guard handles it).
- **Safari's pull-to-refresh** (`WebViewImpl`, `NSRefreshController`) is drawn and triggered from the top rubber-band stretch (`topScrollStretchDidChange`). No stretch, no refresh, so the rule above removes it too. Hence Margin's own.
- **Margin's pull-to-refresh** (`shared/pull.js` logic, unit-tested; indicator in `content/sidebar.js`; setting `pullToRefresh`, default on, only with `blockGestures`). Web pages don't get gesture phases, which Safari uses to ignore momentum and to know when the fingers lift, so they're inferred, erring towards not reloading:
  - **Gesture boundaries:** a gesture is a run of wheel events with no gap over 140ms. It counts only if it started with the page at its top and nothing under the pointer scrolling vertically (like Safari, which tracks only gestures that began at the top). Mouse-wheel notches (single steps over 80px, or line-mode deltas) don't pull.
  - **Momentum:** once 5 deltas in a row each shrink by a steady 72–99%, the rest of the gesture is momentum and doesn't pull. If the pull was already armed, momentum means the fingers lifted: reload.
  - **Arming:** 150px of upward scrolling over at least 8 events and 160ms. When the events stop, an armed pull reloads; anything else cancels.
  - **Indicator:** a dark round badge centered over the page (like the loading pill), sliding down with the pull, its ring filling to the threshold. The arrow flips up when letting go will reload, then it spins and `location.reload()` follows 300ms later (the loading pill is skipped for that unload). If the page stays (a cancelled "Leave page?"), the next click or key, or 10s, clears it. SVG built with DOM calls (Trusted Types pages).
- **Sidebar and palette:** `containScroll` (both browsers) cancels wheel events over Margin's panels unless a list inside them can scroll that way. Their lists have `overscroll-behavior: none` (no bounce, no chaining). While the palette is open, its backdrop doesn't scroll the page either.
- **Tests:** unit tests for the pull tracker (deliberate pull, release early, momentum after arming, flick, scrolling up to the top in one gesture, mouse notches, too short, un-pulling, leaving the top, fresh gestures). E2E (Chromium, Safari profile): the no-bounce rule follows the setting, adds no markup, and isn't in the Chrome build; a trackpad-style pull reloads the page while the same pull scrolled down, a small one, or with the setting off doesn't; and scrolling over the sidebar scrolls only its overflowing tab list, never the page. Mutation-checked: disabling containment or the pull fails them.

## Searches use the browser's search engine (2026-10-25)

- **Tirth's decision:** no search engine of Margin's own (it was DuckDuckGo, with a picker in Settings). Searches from the launcher and the palette follow the browser's setting. The SPEC's M3 line is updated; the old `searchEngine` setting is dropped, also from saved settings.
- **Chrome:** `chrome.search.query` (Chrome 87+) searches with Chrome's default engine, in the launcher's own tab or a new tab. Needs the `search` permission, added for the Chrome build only (`platform/chrome/manifest.json` `add_permissions`; the build appends it to the shared list).
- **Safari has no `search` API** (MDN browser-compat-data: `search.query` not supported in Safari; not in WebKit's extension APIs either) and no way for an extension to read Safari's settings. So Margin learns the engine from the searches Safari itself makes from the address bar, which carry Safari-specific parameters: Google `client=safari`, Bing `form=AP…`, DuckDuckGo `t=osx`/`iphone`/`ipad`, Ecosia `tts=st_asaf_…`, Yahoo `fr=aapl…`/`.tsrc=apple`. These and the URL shapes were cross-checked against SafariKeywordSearch's tests (github.com/arnemart/SafariKeywordSearch). Apple doesn't document them.
  - **Learning:** the background checks every tab navigation, so a change in Safari → Settings → Search is picked up at the next address-bar search. A search typed on an engine's own site has no Safari parameters and doesn't count. At startup it also checks the open tabs, but only if nothing is known yet (a stale tab mustn't undo a newer engine). Tabs Margin itself just searched in are skipped for 30s, since its URLs look like Safari's.
  - **Margin's searches** use the URL Safari makes on macOS for that engine, on the same (regional) host, e.g. `https://www.google.co.uk/search?client=safari&rls=en&q=…&ie=UTF-8&oe=UTF-8`.
  - **Before Margin has seen a Safari search:** Google, Safari's out-of-box default. Settings says so and explains how it follows Safari.
  - **Not recognized:** Baidu, Sogou and 360 Search (Safari's engines in China) carry no Safari parameters, so a Safari search there can't be told from one on their own sites. Margin keeps the last engine it knew.
- **Settings:** the engine picker is gone; a line names the engine searches use and where to change it (the browser's settings).
- **Fix (reported: switched Safari to Yahoo, Margin still searched Google):**
  - **Same-tab skip:** the 30s skip for tabs Margin had just searched in ignored *any* search there, so a Safari address-bar search right after a Margin search in the same tab wasn't learned. Now it skips only the engine Margin itself used; a different engine there is Safari's. Covered by an E2E test, mutation-checked.
  - **Yahoo's URLs** put `;_ylt=…;_ylc=…` into the path; the pattern now allows that.
  - **Reported URLs:** the URL is also checked once a page finishes loading, in case Safari reports a navigation without it.
  - **Diagnostics:** a search on a known engine's site without Safari's parameters is logged with `console.debug` in the background console, with its URL.
  - **Settings** shows when the engine was last seen in Safari's address bar.
  - **Still inherent:** Margin can only learn a new engine once Safari has searched with it from its address bar.

## Pinch to zoom and two-finger swipe back/forward, Margin's (2026-10-25)

- **Pinch to zoom.** Blocking Safari's pinch (for the all-tabs overview) also blocked pinch-to-zoom: once Safari gets a pinch's start, WebKit's magnification takes the rest of the gesture and bypasses the page (`hasActiveMagnificationGesture` in `WebViewImpl::magnifyWithEvent`), so the pinch can't be split between zoom and overview. So the guard now takes every pinch at normal zoom and hands it to Margin, which zooms with Safari's own page zoom (`tabs.setZoom`/`getZoom`, Safari 14+ per MDN's compat data, implemented in WebKit):
  - **Levels:** Safari's zoom levels, nearest to (zoom at the pinch's start × pinch scale): 100, 115, 125, 150, 175, 200, 250, 300%. Never below 100% by pinching, so pinching in can't become the overview; ⌘− still zooms out. If already below 100%, it doesn't go lower.
  - **Feedback:** a small "125%" readout at the top of the page while pinching. The start level is re-read from Safari at each pinch (⌘+/⌘− may have changed it).
  - **Trade-off vs. Safari's pinch:** this is page zoom (the page re-lays out, like ⌘+), not Safari's magnifier, and it steps by level. A page Safari has magnified itself (two-finger double-tap smart zoom) keeps Safari's pinch.
- **Swipe back/forward with Arc's badge** (measured from Tirth's recording):
  - **Badge:** a ~148px dark circle centered on the page card's left edge (back) or right edge (forward), vertically centered, half of it over the sidebar or frame. A bold white arrow sits in its visible half. It fades in and darkens with the swipe; it doesn't slide.
  - **Gesture:** the gesture logic is the pull tracker generalized to the x axis (`createSwipeTracker`: the direction is set by the first sideways movement; 110px, 6 events, 100ms to arm; same momentum, mouse-notch and release rules).
  - **Navigation:** `history.back()`/`forward()` from the page, so same-page (SPA) history works too. The badge fades after 450ms if the page doesn't unload.
  - **When it applies:** only where nothing under the pointer scrolls sideways, as with Safari's swipe; setting `swipeNavigation` (default on, needs `blockGestures`). Direction: fingers moving right (deltaX < 0) go back, like Safari.
- **Settings:** the master switch now reads "Use Margin's trackpad gestures instead of Safari's…", with sub-switches for pull-to-refresh and swipe navigation.
- **Tests:**
  - **Unit:** swipe tracker (both directions, release, reversing, vertical, flick, notches, ineligible), `zoomForPinch` (levels, clamping, the 100% floor, below-100% start), and the guard handing every normal-zoom pinch to `onPinch`.
  - **E2E (Chromium, Safari profile), with real wheel events:** a sideways swipe shows the badge on the left edge and goes back, the other way goes forward; nothing happens over a sideways-scrollable box, for a small swipe, or with the setting off. The background zoom handlers set and read the tab's zoom, clamped. Mutation-checked.
  - **Not testable in Chromium:** real pinch events (a test page can't create a pinch the extension's script sees with a `scale`), so pinch → zoom is a manual check.

## Arc-closer with newer Safari features, each optional (2026-10-25)

Tirth's plan: tell users (on the website) which Safari feature flags give the closest Arc experience. Margin can't turn flags on, so every feature below is detected before use, and without it Margin does exactly what it did before.

- **Reviewed the full Feature Flags list** (Tirth's recording) and checked WebKit's current source (`UnifiedWebPreferences.yaml`) for where each is headed. Useful: CSS corner-shape (Testable in Tirth's Safari; **stable, on by default** in WebKit's development version) and Threaded Time-based Animations (Preview; stable in WebKit's development version, nothing to code). Also used, already stable and on: Navigation API, popover (top layer), HTML switch control. Not useful for Margin: Close Watcher (Esc handling exists), Scroll State Container Queries (minor; JS covers it), SpeculationRules (prefetches for the current document; Margin opens results in new tabs), MediaSession extended actions, Multi-Process Back/Forward Cache, CSS Painting API (worklets can't load from a content script), the rest (media, WebGPU, security/privacy).
- **Squircle corners** (`@supports (corner-shape: squircle)` blocks at the end of sidebar.css, palette.css and newtab.css, and in the placeholder template):
  - **The fit:** rendered at 2× in Chromium (which ships corner-shape) and measured like Arc's corner. `border-radius: 11px; corner-shape: squircle` fits Arc's page corner with error 0.34 vs 3.06 for the 6.25px circle Margin uses otherwise; Margin's actual card measured 0.34. WebKit's shadow painting follows corner shapes (`BackgroundPainter` → `BorderShape`), so the card's shadow matches too.
  - **Everywhere else** (rows, chips, menu, palette, tiles…), radii scale by 1.75 (11/6.25) with the squircle, so each corner keeps its apparent size and gains the continuous curve.
  - **Fallback:** the circular rules stay as they were outside @supports. Unit-tested (no corner-shape outside @supports; fallback radii kept). Checked in WebKitGTK (corner-shape off there): pixel-identical to before. Note that Chrome (which supports it) now shows squircles too.
- **Navigation API:**
  - **Swipe:** a swipe toward no history (`navigation.canGoBack`/`canGoForward` false) shows no badge and does nothing; without the API, as before.
  - **Loading pill:** same-page navigations a site runs through the API (`navigation.intercept`) show the loading pill if they take over 150ms, until `transition.finished`. Sites using plain pushState are unaffected (no signal), as before.
- **Top layer (popover):** the palette host and the tab right-click menu are shown as `popover="manual"` while open, so a site's own popovers or full-screen elements can't cover them. The menu is then placed in viewport coordinates, and the browser's popover defaults are neutralized. Not used while the site has a modal `<dialog>` open (`:modal`): everything outside a modal is inert, top layer included, so the palette would show but take no typing; the z-index fallback applies as before. Without popover support (Safari < 17): z-index, as before.
- **Switch toggles:** Settings checkboxes carry `switch` (macOS-style toggles in Safari 17.4+; plain checkboxes elsewhere).
- **Tests:** E2E (Chromium, Safari profile): squircle radii/shapes applied; the palette in the top layer above a site popover, and not while a site modal is open; the menu in the top layer at the pointer; no badge or navigation toward no history; the pill for a slow intercepted navigation but not a fast one. Mutation-checked: removing the top layer or the history check fails them. Unit: fallbacks and switch attributes.

## Squircles removed: Safari's experimental corner-shape draws squares (2026-10-25)

- **Reported:** with Safari's "CSS corner-shape property" flag on (as recommended), every squircled corner (page card, sidebar rows…) was drawn square.
- **Cause:** in Safari's current build the feature is "Testable": it parses, so `@supports (corner-shape: squircle)` is true and the computed style says `squircle`, but it doesn't draw it correctly. Reproduced the parsing half in WebKitGTK 2.52 with the same flag (status Testable, off by default) turned on: `CSS.supports` true, computed `squircle`, yet drawn as a plain round corner (no squircle). The previous entry assumed @supports meant "draws correctly"; it doesn't for a Testable feature, and a page can't check its own pixels.
- **Fix:** no `corner-shape` anywhere. All corners are the working circular ones again, identical with the flag on or off (checked in WebKitGTK with it on: same corner profile). Unit test: no `corner-shape` in any of Margin's CSS (including styles.js and every placeholder). E2E: plain rounded corners even in Chromium, which supports corner-shape. The README no longer recommends the flag; Follow-ups says when and how to bring squircles back.
- The other enhancements (Navigation API, top layer, switches) are stable features and are kept.

## Injection probe: go/no-go for the transplant shell (2026-10-25)

- **Why:** the only extension-only way found to give pages a truly narrower viewport is the "transplant shell" (research on branch `docs/viewport-research`, `research/viewport/`). It works only if Safari runs `document_start` content scripts while `<html>` is still empty. WebKit's source says it does; real Safari is untested. Nothing of the shell is built until this passes and Tirth agrees.
- **What the probe records** (`shared/probe.js`): what `<html>` held when the script ran (child node names, not just a count), `readyState`, the content type, the navigation type and `responseStart`. Two copies: Margin's manifest content script (`content/sidebar.js`) and a registered one (`content/probe-registered.js`, `scripting.registerContentScripts`, id `margin-probe`), because the shell would be registered and Safari loads registered scripts after the manifest's. Records stay in `storage.session` (not `storage.local`, whose every change re-renders all sidebars), origin and path only, last 500. The palette's "Injection probe results" opens `diag/probe.html` (summary per source, table, Copy report). All of it is temporary and is removed once the question is answered.
- **Verdicts:** pass (`<html>` empty) · foreign (only nodes content scripts added, e.g. another extension's `<style>`; for the registered copy, Margin's own hosts) · late (the parser had added HEAD, BODY, a comment or text) · existing (the page had already parsed: WebKit injects into open pages when the extension loads or gets site access, `InjectUserScriptImmediately::Yes`) · n/a (not `text/html`: Safari's PDF document adds `<head>` before injecting, image and media documents inject into an empty `<html>`) · bfcache (restored, no injection). Found by an adversarial review of the first version, which counted existing and PDF loads as late and images as pass.
- **Decision rule, fixed before the run.** Only manifest rows from text/html loads count, and only in blocks where site access, Margin's on/off state and the extension itself weren't changed (any of those injects into open pages, which can look exactly like late):
  - **GO:** every ordinary navigation row (typed, link, reload, cached, Back/Forward without the cache, new tab, reopened tab, with other extensions on) is pass or foreign. 0 late out of about 40 bounds the late rate at about 7.5% (rule of three), so covering every kind of navigation matters more than the count.
  - **GO with a skip condition:** as above, but late or existing rows show up only right after a launch, session restore or a site-access grant, or only in registered rows right after the extension loads. The shell would skip those loads and use push mode (synthesis.md, fallback ladder).
  - **NO-GO:** a late row with `ready=loading` on an ordinary navigation that comes back when the same step is re-run 5 times. Then the takeover would race on normal loads. A single late that doesn't come back in 10 re-runs is logged as an anomaly. On NO-GO the fallback is the fetch-and-write variant (more limits) or keeping push/overlay.
  - The shell's own skip test must follow the same classification (readyState `loading` and no parser-made child), not "any child": the registered copy runs after `sidebar.js` has added Margin's host.
- **Tests:** unit tests cover the verdicts and summaries. E2E (`tests/e2e/probe.test.js`, Chromium): a manifest record with an empty `<html>` and `ready=loading` at `document_start`, the registered copy (pass or foreign, never HEAD/BODY), and the results page. Mutation-checked: taking the snapshot after parsing fails the first test (`existing`, not `pass`). The loader test that waited for "any registered script" now waits for `margin-docked` by id, since the probe registers one too.
