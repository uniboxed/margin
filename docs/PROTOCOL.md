# The link between Margin's extension and Margin.app, version 2

What each end says, in order. The app's end is margin-core's on every OS (`app/shared/core/src/`: `protocol.rs` the messages, `link.rs` the session, `socket.rs` and `websocket.rs` the WebSocket and the secrets, `relay.rs` Chrome's and Edge's relays, `chunks.rs`, joined for the Mac in `link_hub.rs` and for Windows in `shell/`; the lasting data in `data/`), carried by each OS's transport (the Mac's `app/platforms/macos/shell/ExtensionLink.swift` and `RelayLink.swift`, Windows' `app/platforms/windows/src/tcp.rs` and `pipe.rs`), with the Mac's routing in `Shell.swift`; each copy's state is mirrored by the core too (`mirror.rs`, one per link in `link_hub.rs`; the Mac reads it through `StateMirror.swift`); the extension's end is `extension/background/link.ts` (with `background/app-link.ts`, and what pages read in `shared/app-link.ts`). `tools/app-tests/fake-extension.mts` is a working stand-in for the extension's end, `tests/fake-app.ts` one for the app's.

Version 1 was `feat/native-panel`'s (one link, a `cover` lease for the sidebar panel). Version 2 has one link per browser profile, no lease, `setLayout`, and chunked themes.

## Words

- **Copy:** one running instance of Margin's extension. Safari runs one copy per profile, each with its own background and its own link.
- **Link:** one copy's WebSocket to the app, after `hello`. It's known by its browser and profile (`"safari:<profile>"`).
- **Epoch:** a random id the copy makes for each link (each socket). Everything numbered or answered belongs to one epoch.

## Transport (Safari)

0. **The port.** Safari's background is a page (`background.scripts`, non-persistent). The copy that owns its profile's state opens one lasting `runtime.connectNative` port at its start and posts `{ type: 'ping', at }` on it every 20 s (Phase 0: a port used that often keeps Safari's background page alive; a WebSocket alone doesn't). The handler only answers a ping. What the app dispatches into the extension arrives on this port as `{ name, userInfo: { e: <JSON string> } }`.
1. **Ask.** The copy sends a native message `{ type: 'wantLink', nonce }` (`runtime.sendNativeMessage`). `nonce`: 1–128 characters, new each time. **First, the note (since 2026-11-10):** Margin.app keeps where its link is in the extension's own container, `Library/Caches/margin-link` (`{ v, port, token, key, app: { version }, pid, at }`, owner-only, replaced whole as the listener gets its port and as the token changes, removed when it stops; `ExtensionLink.swift` `LinkNote`). The handler reads it and, if the process that wrote it is a Margin.app running now, answers this copy's ask with the link itself: the reply is `{ ok, appOpen: true, launching: false, profile, link: { v, nonce, port, token, key, app, at } }`, as step 2's `link` would carry it, and nothing is passed on or dispatched. The copy takes it as step 2's answer (its `v` and `nonce` checked). Only to the copy that asked, in milliseconds, with nothing Safari can refuse: the app's `dispatchMessage` was refused 15% of the time (`SFErrorDomain 1`) and once for 10 minutes in a row (2026-11-09). With no such note, the extension handler (`app/engines/webkit/safari/handler/SafariWebExtensionHandler.swift`) passes on only `{ type, nonce }`, as the distributed notification `com.unibox.margin.setup` (any process may hear it, so nothing secret goes in it). Its reply: `{ ok, appOpen, launching }`. If Margin.app isn't running, the handler starts it (`NSWorkspace.openApplication`, not activated; at most once per 10 s per handler process), leaving a note in its own container (`Library/Caches/margin-launch`) that the app reads at launch to show no set-up window (a sandboxed caller's `arguments` never reach the app) and says `launching: true`; the notification is lost while the app starts, so the copy asks again every 0.5 s for 10 s (and at once on `appUp`). `appOpen: false` and not launching: the app is gone. **The reply may never come:** Safari 27.2 answers only one of several native messages that its profiles' copies send at the same moment (seen 2026-11-06: five copies starting together after an update, each wantLink reaching the handler, one reply delivered, the other four `sendNativeMessage` promises never settled, for over 10 minutes). So the copy waits for the reply at most 3 s (`REPLY_WAIT_MS`) and takes its `link` (step 2) as soon as it comes, replied or not. Only a copy whose profile id Safari hasn't given yet (none kept from an earlier reply: Transport's `hello.profile`) waits for the reply before linking, so its hello says Safari's id; a reply lost then is asked again.
2. **Answer (without the note).** The app answers into the extension with `SFSafariApplication.dispatchMessage(withName: 'link', userInfo: { e: <JSON string> })`, the JSON being `{ v: 2, nonce, port, token, key, app: { version }, at }`. A copy takes only the answer carrying its own nonce: every copy receives every dispatch (`link` and `appUp`), whichever profile's window is in front (seen 2026-11-06, five profiles).
3. **Connect.** The copy opens `ws://127.0.0.1:<port>/?t=<token>`. The app refuses (HTTP 403, before any WebSocket opens) a wrong token, a path other than `/`, and an `Origin` that isn't `safari-web-extension://…`. It listens on 127.0.0.1 only.
4. **Welcome.** The app's first message is `{ k: 'welcome', v: 2, key }`. The copy closes the socket unless `key` is the one from step 2 (the app proving it's the app).
5. **Hello.** The copy's first message is `hello` (below), then its `snapshot`. A socket that says nothing within 5 s of opening is closed.
6. **App up.** When the app starts while Safari has been running for 2 s, it dispatches `appUp { v: 2, at }`: every copy should ask again (step 1). The app never dispatches while Safari isn't running (that would open Safari).
7. **Kept.** The copy keeps `{ port, token, key }` in `storage.session` once welcomed: its background starting again tries that first (0.4 s), then asks.
8. **Again.** A drop (the socket closed, or nothing from the app for 40 s) is tried again with the kept link after 0.25, 0.5, 1, 2 and 4 s, then asked for (step 1), then every 5 s doubling to 60 s, and whenever a page starts. The handler saying the app is open but no `link` coming, it's asked again after 5 s up to 3 times in a row before the doubling goes on (an app replaced by an update quits once it notices, and the handler starts the new one). After the app's `bye`, only `appUp` or a page starting asks again soon. One try at a time: asked for while one is under way (`appUp`, a page starting, the new-tab page's Start or Try again), the copy asks again as soon as that try ends unlinked, whatever it was waiting on. No reply and no link within the 3 s: asked again after 5–7.5 s (spread a little, as the other copies that asked with it are), up to 3 times in a row, then the doubling. A try under way 45 s (`STUCK_MS`: something it waits on never ended) is left and a new one made; every ping (20 s) an unlinked copy checks it has a try under way or one to come.
9. **No socket where it would hang.** The copy makes a WebSocket only in a document (a worker's hangs WebKit's background: `feat/native-panel`, 2026-10-30). It notes each socket it opens (storage.local `appLinkOpening`) until the socket's handlers are on, and removes the note only after that, never awaiting storage between `new WebSocket` and its handlers. A background that finds the note left turns sockets off for the rest of that Safari session (storage.session `appLinkSessionOff { at, why }`) and counts the sighting (storage.local `appLinkHung { count, at }`). Found again in a later session before any link opened, sockets stay off for 24 h (storage.local `appLinkOff { at, until, count, why }`, honoured only until `until`; an older `{ v }` is removed). A link that opens says the sightings in its `hello` (`socketsOff`) and clears the count. Pages see `appLink.why: 'sockets-off'` with `offAt` and `offUntil`. The new-tab page's Try again (the page request `retryLink`) clears all of it and asks at once. Each time the guard turns sockets off, the copy says so in Margin.app's log.
10. **What the log says.** Every close has a code and a reason. The app logs a close frame's (`closed by the extension (1001 going away)`, `(1005, no status code)` for none, `(1006, no close frame)` for a TCP end), every socket that ends before its hello, and its listener's `waiting`, `setup` and `cancelled` states. A listener waiting 5 s is made again, on a new port. The copy notes its background starting (whether it had a kept link, the pages' state before it, and how the last link ended: storage.session `appLinkLast { what, why, at }`), each try of the kept link and how it went, its native port going and coming back (at most once a minute), and a link check that ran late (`paused N s`). A late check judges nothing itself: it sends a `tock` as a probe, the link is judged after the socket's queued messages, and the app's quiet counts from the probe. The copy's notes go to the app's log over the native port as `{ type: 'log', line }`, at most 300 characters, never an address or a title. Up to 20 made while the port is down are sent once it's back, each as `(at HH:MM:SS.mmm) …`.

After the last link closes, the app keeps its token and key for 30 s (a copy that restarts tries the link it had first), then makes new ones; a copy whose connection is refused asks again.

## Transport (Chrome and Edge, on the Mac)

The same link as Safari's, from step 3 on: the copy's WebSocket to `127.0.0.1`, `welcome`, `hello`, every message the same. Only how the copy finds the app differs: there's no `dispatchMessage`, so Margin's connector inside Margin.app (`Margin.app/Contents/Helpers/margin-connector`, Rust, `app/shared/connector/`, the same program on every OS) does what Safari's extension handler does. Below, "the relay" is that connector as the browser starts it.

1. **The host.** Margin.app runs `margin-connector --install` at each launch, which writes the native-messaging host files (the browsers and where their files go: `app/engines/chromium/`, crate `margin-chromium`): `com.unibox.margin.json` in each browser's `NativeMessagingHosts` folder under `~/Library/Application Support/` (Chrome and its Beta, Dev and Canary, Edge and its Beta, Dev and Canary, Brave, Chromium, wherever the browser's folder exists; on Linux under `~/.config/`; on Windows one file and each browser's registry key), naming the connector and only Margin's extension (`allowed_origins`, the id from the Chrome build's `key`). A file that already says the same is left alone.
2. **The relay.** The browser starts one relay per native port (`connectNative`) and one per one-off message (`sendNativeMessage`), each with the browser's own framing on stdin and stdout (4-byte native-order length, then UTF-8 JSON). The relay connects to the app's connector socket (`~/Library/Application Support/Margin/connector.sock`, mode 0600; the app checks that its peer is the same user and, in a signed build, the connector signed by Margin's team as `com.unibox.margin.connector`) and says `{ k: 'relay', v: 1, version, pid, browser, waited }`: `pid` the browser's process (the relay's parent), `browser` `chrome` or `edge` (from that process's program name), `waited` true once it had to wait for the app. The app answers `{ k: 'relayWelcome', v: 1, version }`; a relay whose `version` differs exits (the browser starts the new one next time). Then each of the browser's messages goes to the app as `{ msg }`, one JSON line each, and each line the app sends goes to the browser as it is.
3. **What the app answers.** Every message gets the reply Safari's handler gives (`{ ok, appOpen, launching }`), with `browser` and `pid`: a `wantLink` (with its nonce) is then answered as Safari's (Transport (Safari), step 2), by dispatching `{ name: 'link', userInfo: { e } }` into every relay of that browser process, where the copy's lasting port receives it as it would Safari's dispatch. `appUp` goes the same way to a relay that says `waited`. The app not running: the relay starts it (in the background, never activated, at most once per 10 s), answers `{ ok: true, appOpen: false, launching: true }` itself, and keeps trying the socket; a lasting port's relay stays and says `waited` once in.
4. **Connect.** As Safari's, with the copy's Origin `chrome-extension://…`. Chrome's background is a service worker, and a WebSocket there is fine (WebKit's hang, step 9, is Safari's): the socket guard is Safari's alone. The copy's lasting port and the link's ticks keep the worker alive.

**On Windows** it's the same (`docs/windows/BRIEF.md`): the connector is `margin-connector.exe` beside `margin.exe`, the app's connector socket is its named pipe `\\.\pipe\Margin-<user SID>` (this user only; each end checks the other is Margin's), the browser is the connector's first ancestor that isn't `cmd.exe`, and the host file is one file under `%LOCALAPPDATA%\Margin` named in each browser's registry key. The link is the copy's WebSocket to `127.0.0.1`, as here.

A copy in Chrome or Edge says `browser` and `pid` in its `hello` as the relay told it. The app trusts them, and never refuses a link for them; a `pid` that no relay's hello has named since the app started is logged as a warning at link up (both apps: `Shell.unheardPid`, margin-core's `warn_unheard_pid`). Its `profile` is its own (`p-…`): Chromium gives an extension no profile id.

## Messages

One JSON object per WebSocket text frame. `k` names the kind. Unknown kinds are ignored by both ends. Numbers are JSON numbers; ids are integers.

| `data.need`, `data.snapshot`, `data.changes`, `data.ack` | per `docs/DATA.md` | `data.need { all: true }`: answered with the converter's `data.snapshot`. `data.snapshot { format, set, transfer, part, parts, rev?, omitted? }`: once all `parts` of a `transfer` are here, their items put together, with this copy's changes since its `data.hello` merged on top and the items in part 0's `omitted` kept as the copy has them, it's the copy's cache (`stateFromDataSet`, the app's times kept for what agrees with it, so none of it is queued back); part 0's `rev` is kept once it's applied. `data.changes { changes }`: merged into the cache by the same rule as the app's. `data.ack { upTo, rev? }`: `upTo` kept as `acked` (never lower), `rev` when there is one. The `rev` is dropped when the cache stops being the app's set (storage that started from defaults). |
| `theme` | as above | The app may send a theme the same way (once it holds user themes, step 3). |
| `data.need`, `data.snapshot`, `data.changes`, `data.ack` | see `docs/DATA.md` | The lasting data: asking for the whole set, the app's set (in parts), its changes, and what it has stored (`docs/DATA.md` "Messages"). |

### The handoff (removed: 2026-11-16 in the app, 2026-11-17 in the extension; `setWindowState` and `closeWindow` stay, for the host)

Margin.app's switch to another profile's window under a still screen, with the old window parked instead of closed (`docs/HANDOFF.md`). These words are in margin-core's `protocol.rs` (`AppMessage::Parked`, `ParkedActivity`, `HandoffRequest`, the answers) and `background/link.ts` (`APP_REQUESTS`, `WINDOW_CALLS`, `windowCallRefusal`, `parkedActivity`). The copy's end is `background/handoff.ts`, `background/handlers.ts`, `background/sleep.ts` (`windowDrafts`) and `shared/frame-probe.ts`; the app's comes with the handoff's later work packages.

**Times.** `notAfter`, `landedAt`, `firstAt`, `lastAt` and `visibleAt` are `Date.now()` milliseconds: the app and its copies read the same clock.

**`parked { epoch, windowId, on, at }`** (app → copy). The copy keeps it per window, this epoch's only (a new epoch clears it), and uses it to:

- tell the app when a parked window is used (`parkedActivity`, below);
- prefer a tab in a window that isn't parked for `focusTab` and `openPin`, and ask the app (`why: 'raise'`) instead of raising a parked window;
- keep a parked window's tab in front from sleeping.

**`push { type: 'parkedActivity', windowId, tabId?, why }`** (copy → app). The push's own `windowId` is the same window. The app takes it out of the pushes (`LinkMessage.parkedActivity`): no overlay hears it. `why`:

- `tab`: a tab Margin didn't open was made in the parked window (a link from another app). Names its `tabId`.
- `focus`: `windows.onFocusChanged` named the parked window, and not within 1 s of Margin's own windows call for it (Safari's Window menu, ⌘`, the Dock's window list). The person's choice: no tab.
- `raise`: Margin's UI asked for a tab (`focusTab`, `openPin`) whose only match is in the parked window. Names its `tabId`.

The app merges a burst into one (150 ms), ignores it while a switch is busy or watching that window, and hands off to that window. A malformed one (no window, a `why` not known, a tab's or a raise with no tab, the push and the msg naming two windows) isn't a message.

**Requests.** All are `req`s like any other (`APP_REQUESTS`), each with the window in its payload:

| `type` | Payload | Answer (the reply's `result`) |
|---|---|---|
| `setWindowState` | `windowId`, `state: 'fullscreen' \| 'normal'`, `focused?`, `notAfter`, `land?` | `windows.update(windowId, { state, focused? })`, then `windows.get` every 100 ms until the state lands (at most 3 s), then the `windows` list at once (not after `WINDOWS_MS`). `{ windowId, state, landedAt }`, or `{ windowId, state, timedOut: true }`. Not `focusWindow`: `normal` leaves focus where it is. With `land: false` (Margin.app, for a window it hosts, since 2026-11-17): answered `{ windowId, state, asked: true }` as soon as Safari took the update, with no wait for the state and the window free for the next call at once: the app moves the window out of its new full-screen Space within ~0.2 s, so Safari never reports `fullscreen` for it, and the app reads what the window did from the window server. |
| `frameProbe` | `windowId`, `width`, `height`, `frames` (6), `nudgeMs` (80), `timeoutMs` (400) | Passed to the window's tab in front (`tabs.sendMessage`). The page nudges (a 1×1 fixed element outside the layout, alpha 0.01 and 0.02 on alternate frames) for `nudgeMs` and on until it answers, and counts `frames` animation frames after `nudgeMs` with its window at that size (`outerWidth` and `outerHeight` within 2 pt; a size of 0 isn't checked). `{ tabId, frames, firstAt, lastAt, width, height, hasFocus, visible, visibleAt? }` (`width`, `height`: the window's size the page sees at the last frame; `visibleAt`: its last `visibilitychange` to visible), or `{ none: 'no page' }` when the tab doesn't answer in `timeoutMs`. Margin's new-tab page answers the same way. |
| `windowDrafts` | `windowId` | The window's tabs with typed text not sent (the sleeping tabs' draft check, every tab at once, 400 ms in all): `{ drafts: [tabId], unknown: [tabId] }` (`unknown`: a web page that couldn't say in time; a tab that isn't a web page, or has no page loaded, isn't asked). The app closes the window only when both are empty. Safari not listing the window's tabs in time answers `ok: false`. |
| `focusWindow`, `closeWindow` | as above, plus `notAfter?` | As above. With no `notAfter` (today's switch) they're never late or `busy`, as before; they count as pending for a handoff's call all the same. |

**The windows calls** (`WINDOW_CALLS`: `setWindowState`, `focusWindow`, `closeWindow`). Safari carries out a windows call stuck behind a hung tab when it gets to it, and a call made can't be taken back. So the copy checks each one as it arrives, before it calls Safari (`windowCallRefusal`):

- past its `notAfter`: `{ refused: 'late', pastMs }`, nothing done;
- another windows call for that window still pending: `{ busy: true }`, nothing done. The app reads a `busy` as a stuck window.
- A request with no `notAfter` (today's switch) is never late.

Both are ordinary answers (`ok: true`), so the app tells them from a failure (`ok: false`). `WindowCallAnswer` reads them.

**The overlay page and the app, during a switch** (the overlay's `post`, not the link):

- `framed { mode }`: after the shell's `shown` push, on its next animation frame, the overlay page says it has drawn, and whether as `fullscreen` or `windowed` (`OverlayFramed`). The switch waits for B's overlay to say `fullscreen` (R4, at most 200 ms).
- `perform('switch.coverShown')`: the "switching" cover has been in A's overlay for 2 animation frames and no swipe is settling (`docs/HANDOFF.md` §7).

### Liveness

The app ticks every 5 s and closes a link it hasn't heard anything from for 40 s (1001). The copy does the same: nothing from the app for 40 s and it closes the socket and tries again (Transport, step 8). (12 s until 2026-11-07: Safari slows a background page while it isn't in front, and a quiet link then read as gone.)

### Requests (since 2026-11-24, `docs/LINK-RESILIENCE.md` §1)

A `req` ends only on evidence, never after a fixed time (margin-core `link.rs`): its `reply`; the link going down (closed, replaced, or 40 s of silence: `down`); the app's `cancel` (no answer at all, a later reply left); or lost. Lost: a numbered `tock` of a tick sent after the `req`, with no `ack` for it, means the copy read past it without taking it (its socket is in order, and both come from its socket's handler). It's sent once more with the same id (the copy dedupes), and a second time is `lost`. Any bytes say a copy is alive (the 40 s rule only); an `ack`, a `reply` or a numbered `tock` say it's reading. A copy alive but not reading is slow, not gone: its requests wait, and the app can say how long its oldest unacked one has (`Link::slow`). An older copy (no `ack`, tocks without `seq`) is life only, never lost; an older app ignores `ack`. A new link starts with nothing waiting: no old id is sent into it.

The copy (`background/link.ts`) acks each `req` before it runs and keeps this epoch's last 64 ids: one running is left (its reply comes), one answered gets its reply again (unless it was over 64 KB: then `ok: false`, that it's no longer kept). The newest `hostShow` for a window wins: an older one still running for it stops before its next Safari call and answers `ok: false, error: 'overtaken'`. After a detected pause (a link check due over 3 checks ago, seen by the check or by the app's first word after it), the `req`s read are started one turn of the event loop later: a `cancel` behind one drops it, and of several `hostShow`s for one window only the newest runs (the older answered `overtaken`). Its own waits while it links (the ask's pacing, the handler's answer, the app's `link`, the welcome) are advanced by any extension event it hears (windows and tabs events, a page's message, the native port's): Safari's events come on time while a slowed background's timers don't. A wait that would give up but ran over 1.5× late waits again from then, and only one on time gives up; a try in which that happened isn't counted in the ask's doubling.

### A link dropping

- **The app** (`Shell.swift`) keeps a dropped link's overlays where they are for 6 s, dimmed, with "Reconnecting to Safari…": the copy linking again in that time takes them back as they were (theme and keys kept, the state sent again), else they close. A link replaced by a newer one, a `bye`, or the app quitting closes them at once.
- **The copy** tells its pages (`appLink`, below) `reconnecting` on a drop, and `off` once it's clear the app is gone: 6 s with no link, the handler saying the app isn't running, or the app's `bye` (at once). Only then do pages draw their own UI again.

### What pages know

storage.local `appLink`: `{ state: 'linked' | 'reconnecting' | 'off', epoch, at, drawn: { [windowId]: boolean }, why? }` (`why: 'no-link'` only while `off` because the app is running but sent no link: the new-tab page says it isn't answering; `why: 'sockets-off'` with `offAt` and `offUntil`? while the copy's socket guard has its link off: Transport, step 9), written only by the copy that owns the state (a new state at once, `drawn` within 0.12 s), and read with every page's state (`shared/app-link.ts`). While `linked` or `reconnecting`, pages draw no Margin UI (and no page has a box: the page box, with `layouts` and `lastLayouts` here, was removed 2026-11-16). `drawn` holds the app's `drawn` messages, this epoch's only: a new epoch's hello clears it, going off clears it, and a background starting again keeps only the windows `windows.getAll()` still lists. In a window with `drawn` false, Margin's keys go the unlinked way (`shared/app-link.ts` drawsWindow). The window's tab in front is sent `{ type: 'appDrawn', windowId, drawn }` at once; a page's `hello` answer carries `app: { state, drawn? }` (null when off).

### Notices, loading and gestures

What pages said or drew in their own UI before Margin 2 Phase 2 step 5, the overlay of their window says now (step 7). The copy decides; the overlay draws it through the theme's parts. No change to the app's Swift: these are `push` messages, passed to the window's overlay as they come (an overlay made later hears the next one).

- **Notices.** `push { type: 'notice', kind, tabId? }`. The copy sends only a kind and the tab it's about, never words: the overlay has Margin's words for each kind (`extension/shared/notices.ts`) and draws them in the theme's guarded `notice` part (`app/shared/ui/themes/README.md`); an unknown kind is ignored. Kinds: `not-responding` (the page in front is cut off from Margin: its content-script world is bound to a copy that's gone, `background/cut-off.ts`; buttons Reload and Not now), `updated-while-open` (the page in front is bound to an older copy Safari keeps running beside this one; OK), `new-tab-setting` (a new tab from nothing opened the same web page twice: Safari's "New tabs open with" isn't Margin, `extension/engines/webkit/safari/newtab-hint.ts`; OK and Don't show again). One at a time, the newest in place of the one before. A notice about a tab goes once that tab has been the window's tab in front and no longer is, or after its time (15–20 s). The copy says each once per page (`background/notices.ts`: again only 10 minutes after it went by itself, never once a button was chosen). A button comes back as `req noticeAction { notice: kind, action, tabId? }`: Reload loads the page again (a GET of its address, as Margin loads a cut-off page behind), Don't show again turns `settings.newTabHint` off, the others only close it; anything else is answered `false`. Not linked, nothing is said.
- **A switch that didn't happen.** `push switch-failed` with a `reason`, or a switch the overlay asked for itself (`activateTab`, `openPin`) answered `ok: false` or not answered in 15 s, puts up the notice for why (`shared/notices.ts switchFailure`): `tab-gone` ("That tab is no longer open."), `no-answer` ("Margin didn't answer…"), `not-shown` ("Margin couldn't show that tab…"), for 4 s. None with no reason, for a link that's down (the overlay says it's reconnecting), or for a copy that stood back for a newer one.
- **Loading.** `push { type: 'loading', tabIds }`: the window's tabs loading now, the whole set, 16 ms after it changes, and for every window again when the link comes (`background/page-loads.ts`). A tab is loading from its status (`tabs.onUpdated` loading, until complete), from its page being left (`beforeunload`, told at once by Margin's script there: the page request `pageLoading { on, why: 'leaving' }`, taken back if the page stays), and from a site's own same-page navigation taking over 150 ms (the Navigation API's transitions: `why: 'navigating'`); each sign lasts at most 10–15 s. Not stored: every write of storage reaches every page. The overlay's host marks those tabs `loading` (the view model's rows and `tab.loading`).
- **Gestures.** `push { type: 'gesture', tabId, kind: 'pull' | 'swipe', state: 'pulling' | 'armed' | 'trigger' | 'idle', progress: 0–1, direction: -1 | 0 | 1 }`: Margin's pull to refresh and swipe back and forward, which run in the page (`content/trackpad.ts`), told as they go (a change of state at once, the progress in steps of 0.05 at most every 30 ms; nothing while idle) through the copy (the page request `gesture`) for the overlay to draw (the view model's `gesture`). `trigger` shows for 450 ms; a gesture with no word for 1 s goes.

### Sizes

- Nothing the app sends is over **1 MB** of UTF-8 JSON (Chrome closes a native port on a bigger message from the host; the same cap is kept for Safari). The app refuses to send a bigger one rather than send it.
- The app takes messages up to 64 MB (a first snapshot holds every site icon).

### Chunks

A theme package is sent as the UTF-8 JSON of `{ id, manifest, html, css, files: { path: base64 } }` (`background/theme-package.ts` ThemeMessage), cut into pieces of at most 512 KB of bytes, each sent as `theme { id, transfer, part, parts, size, data }`: `transfer` the SHA-256 (64 lower-case hex) of the whole, `part` from 0, `parts` 1–64, `size` the whole's bytes, `data` the piece as base64. Pieces may come in any order. A piece with another `transfer` starts over (the older one is dropped). The whole is used only if its size and SHA-256 match, and it's at most 8 MB. The receiver checks the package again as any theme (`ui/theme-loader.ts loadTheme`).

A theme the overlay can't draw (refused by the checks, missing or broken, or with a page slot under 200 × 150 pt or outside the window) is replaced there by Arcadia, which the app bundles beside the overlay (`dist/app/arcadia.js`, written by `scripts/build.ts`; a script, since the overlay's policy allows no connections). The overlay says ready as usual and puts up its own notice, `theme-failed` ("Margin couldn’t draw the theme you chose, so it’s using Arcadia for now…", Settings and OK). That notice's buttons stay in the overlay: Settings asks the copy for `openLauncher { settings: true }`, and no `noticeAction` is sent. The profile's `settings.theme` is left as it was, so the next package the copy sends is tried again. The log says the theme's id and the kinds of what was wrong, nothing from its files.

## What the app does with it

- One mirror per link (margin-core's `mirror.rs`, kept per link by `link_hub.rs` on the Mac and `shell/` on Windows); deltas apply in order; a gap asks for a resync, and until the snapshot comes, deltas are ignored.
- Windows: bound to the window server's from evidence, never guessed (`WindowMatcher.swift`, PLAN.md §5): made by the app's own `openSpaceWindow`; created or focused (`createdAt`, `focusedAt`) as a new or new front window server window appeared, each alone then; the only free window with its bounds; visible (`visible`, `visibleAt`: its page alone says it's shown, since the last Space change or new front window, and it's the only window on screen with its bounds); or settled focus within one copy (a copy's `focused` is about its own windows only). A binding holds while both windows exist; a new copy (another `instanceId`) drops its link's bindings, since its window ids may be new. A window not bound has nothing drawn over it. A full-screen window of a linked copy gets an overlay drawing the theme once the copy's state and theme are here.
- The lasting data: one data set per browser profile in the app's files (`docs/DATA.md` "The app's files"); a link's data messages touch only its own profile's set.
- A `push` of `palette` for a window whose overlay isn't shown (not made yet, its window not bound, or not on screen) is held up to 1.5 s and given to the overlay as it shows, else dropped and logged (`palette push for window N (…): no overlay drawn there …`): a palette never opens in an overlay that isn't on screen. Dropped, the copy is told `drawn` false for the window at once (not after its grace) and, for a `newTab` one, asked `paletteDropped`, so ⌘T still opens Margin's new-tab page. A `push` of `keyHeard` is logged by the app (with whether its hot keys were on, and why not: the front window has no overlay shown, the front app isn't a linked browser), not passed to the overlay.
- Each overlay's page gets the stored values and passes changes on as they come (`app/shared/ui/host-app.ts`); its actions come back as `req` for its window; its layout goes out as `setLayout`.
- A parked window's overlay, and the overlay of a switch's target, get no `windows` list until the copy's list says that window is full screen (then the latest list goes). Their `hello` says `mode: 'fullscreen'`, and their layout changes send no `setLayout`. The page takes its mode from its own window's state in each list, so a parked window (normal while parked) would otherwise flip to `windowed` and lose its full-screen layout. Shown again, its slot is the same size in the same mode: no `setLayout` goes. A parked window's overlay is hidden, never closed, and gets no palette (`docs/HANDOFF.md` §2.3, §2.4).
- Spaces across profiles (`docs/DATA.md` "Spaces across profiles"): each overlay also gets `across` (every profile's spaces in the one order, the profiles' names: with Full Disk Access Safari's own, `nameFrom: "safari"`, with Safari's symbol as a small PNG `symbol`; `profile.rename` then changes only the emoji and color), in its hello and as `{ type: 'across' }`. An action on another profile's space never goes to the window's copy: the page asks the app (`perform`: `profile.switch`, `profile.space` for a space made, renamed or deleted in another profile, `profile.rename`, `profile.forget`, `space.move`), and the app does it through that profile's link (or its data set, when it isn't linked). The next/previous space keys follow the one order: within a profile they're the copy's `navigate` (or `setSpace` when the order skips around), across profiles the app's switch.
- The switch between profiles in `across` (`docs/HANDOFF.md` §5, §7): `switching { profile, space, phase, from?, notice?, noticeKind?, noticeProfile?, noticeIn? }` and `switchSettings { closeWindows }`. `from { profile, windowId }` is the window the switch leaves: its overlay alone draws the "switching" cover, while `phase` is `preparing`, `waitingForLink` or `frozen`. `noticeKind` is one of the switch's notices (`window-kept-draft`, `dialog-open`, `window-busy`, `late-landing`, `window-on-desktop`, about `noticeProfile`), in the words the overlay has for it (`shared/across.ts` `SWITCH_NOTICES`), shown only in the overlay of `noticeIn { profile, windowId }` when it's given; `notice` is the app's own text, as before. `switchSettings.closeWindows` is "Close windows to save memory", one value for the browser (`browser.json` `switching`). The page asks the app (`perform`) for `switch.closeWindows { on }`, says `switch.coverShown`, and passes a button of the switch's notice back as `switch.notice { kind, action }` (`window-kept-draft`'s `close` closes the kept window by its copy, no drafts check).

### iCloud Tabs (removed 2026-11-17, to be rebuilt later; history)

The tabs open in Safari on the person's other devices, which the app reads itself from Safari's `CloudTabs.db` with Full Disk Access (`app/engines/webkit/safari/CloudTabs.swift`, read only, `DECISIONS.md` "Margin 2: iCloud Tabs"). They never go through the extension: the app gives them straight to its own web views, the same way it gives `across`.

- **When:** the app reads while a Safari copy is linked whose settings don't have `showCloudTabs: false` (Settings' "Show iCloud Tabs"); it starts and stops as links come and go and as a copy's `snapshot` or a `delta` of `settings` says. Chrome and Edge overlays get nothing (Phase 5: `sessions.getDevices()`).
- **What:** each Safari overlay's hello has `cloudTabs` (null until read, or for another browser), and the overlay gets `{ type: 'cloudTabs', cloudTabs }` whenever it changed (the same JSON is never sent twice to one overlay; null once the reads stop). `cloudTabs`: `{ status, devices }`, `status` one of `ready`, `noAccess` (no Full Disk Access), `noData` (no file: iCloud Tabs off or never synced), `failed` (not Safari 27.2's tables); `devices` (only with `ready`) the other devices with tabs, the one used most recently first: `{ id, name, kind: 'phone' | 'pad' | 'mac' | 'vision' | 'other', model, modifiedAt, ephemeral, duplicateName, tabs: [{ id, title, url, pinned, viewedAt }] }`, tabs in the device's own order, web pages only, times in milliseconds since 1970 (`modifiedAt` is Safari's record time, rounded to the local day; `viewedAt` 0 when Safari has none). This Mac's own rows are left out. The page checks it again (`extension/shared/cloud-tabs.ts cloudOf`) and keeps it as the state's `cloudTabs` (`ui/host-app.ts`).
- **Reads:** after a file change, at most once a second, and none when `CloudTabs.db` and its `-wal` have the same size, time and inode as at the last good read; no access or no file is tried again every 10 s, a busy database after 2 s. The log says counts only (`icloud tabs: …`), never a title, an address or a name.
- **What the overlay asks** (`perform`): `cloud.access` (System Settings at Full Disk Access, the URL the set-up window's step opens) and `copyText { text }` (up to 8,192 characters, to the pasteboard: an iCloud tab's Copy Link). Opening an iCloud tab is an ordinary `req`: `newTab { windowId, url }`, or `openHere` over Margin's new-tab page, as for an address typed in the palette.

### Installed apps (the app's own data, to its overlays)

The Mac's apps Margin can open in its page area (`docs/MARGIN-APP.md`, phase 4), read by the app itself (`app/platforms/macos/shell/AppCatalog.swift`, `ShellApps.swift`). Off unless `MarginHosted` is set in the app's defaults (`Shell.Options.hosted`): off, nothing is read, the hellos say `apps: null` and nothing is pushed.

- **Read from:** `/Applications`, `/Applications/Utilities`, `/System/Applications` (and its `Utilities`), `~/Applications`, `/System/Library/CoreServices/Applications` (each with one level of plain subfolders; a hidden item left out, but a link to an app: Safari, a hidden link into the system's cryptex since macOS 13), then what Spotlight lists as an application elsewhere, outside other bundles, the Trash, hidden folders, `/Volumes`, `/Library`, `/System`, `~/Library`. One entry per bundle id (the first folder's). Read off the main thread at start, then again 2 s after a change in those folders (FSEvents) or in Spotlight's list.
- **Which apps:** `AppCatalog.hostable`, the one rule: an application bundle (`CFBundlePackageType` `APPL` or none) with a bundle id; not `LSUIElement` or `LSBackgroundOnly` (agents and background apps); not Margin itself; not an installer or uninstaller, nor Finder and the system's own parts.
- **What:** each overlay's hello has `apps`, and every overlay gets `{ type: 'apps', apps }` whenever the list changed (the same JSON is never sent twice to one overlay): `[{ bundleId, name, icon }]`, sorted by name, `name` as Finder shows it (localized), `icon` a 64 px PNG data URL (sharp up to 32 pt on a 2x display; a linked app's without the alias arrow; cached in `~/Library/Application Support/Margin/cache/app-icons/`, by bundle id, the app's `Info.plist` time and the size: `<id>@<stamp>@<pixels>.png`, an icon of another size made again) or null. About 8 kB of JSON per app (89 apps: 714 kB). The page checks it again (`extension/shared/apps.ts appsOf`) and keeps it as the state's `apps` (`ui/host-app.ts`); the palette finds them (`shared/search.ts`), and every row, tile and the loader of an app item shows its app's icon from it, by bundle id (`shared/view.ts iconFor`, `ui/view-model.ts`). The log says counts only.
- **What the overlay asks** (`perform`): `app.open { bundleId }`: in Margin's own window, an item of the window's space for that app (the one it has, else a new one) shown in the page area ("Hosted windows"); Safari picked is a new web item in Safari instead, Chrome and Edge are not hosted yet (only logged). Over a browser's window, the app's `Shell.openApp`, the same.

- **The sidebar's width, dragged** (`perform`, Margin's own window only): `sidebar.resizing { on }`, once as a drag of the theme's `m-resize` handle first changes the width and once when it's over (or both at once for a double-click's reset), the second always after the `layout` of the width it ended on (`ui/behaviors/resize.ts`). While it's on and a window is hosted above the page area, the app holds that window's placing and keeps Margin's window in front of it; when it's over, the hosted window is placed once at the page area as it is then (`HostedSession.sidebarResizing`). The width itself is the theme's `sidebarWidth` setting, saved as ever (`updateThemeSettings`).

### Hosted windows (Margin.app's own window, `MarginHosted`)

With `MarginHosted` on, the app owns the spaces and their items (its library, `docs/MARGIN-APP.md`) and shows them in its own window: an app item's app, or one Safari window per profile in use, hosted beside Margin's window by the app's host engine (`app/platforms/macos/shell/HostedSession.swift`). The copy only drives that window's tabs; nothing here touches its own spaces (its usual tab tracking goes on). Off, none of these is sent.

- `newWindow { fullscreen: false }` (as above): the hosted window for this profile, asked once the copy has linked; the app knows it by the `windowId` answered. Closed with `closeWindow { windowId }` when the app lets it go. Two fields for Chrome's and Edge's copies (docs/HOSTED-WINDOWS-CHROMIUM.md §3.2), the app's only: `hosted: true`, the window is the app's from its making (Chromium's own "Margin full screen" leaves it alone, and it counts as in full screen for "only in full screen"); `mark` (8 to 40 letters or numerals), the window opened at Margin's new-tab page with `?mark=<mark>`, whose title is then `Margin <mark>` until an item is shown there (how Windows finds the window's `HWND`; it also makes the window hosted). Safari's copies take them the same way; the Mac app sends neither to Safari.
- `hostShow { windowId, itemId, url }`: the item's page shown in that window (`background/hosted.ts`). The tab tagged with the item before (still open there) is used again; else a tab of that window at the same address that no other item has; else the window's lone new-tab page is sent there; else a new tab. It comes to the front. `url`: `http(s)` or `about:blank` only; `itemId`: the library's item id (1–256 of `A-Z a-z 0-9 _ . : -`). Answered `{ tabId, created }`. The tags are the copy's memory only: a copy started again finds an item's tab by its address.
- `hostClose { itemId }`: the item's tab closed (closed from Margin's sidebar). Answered `{ closed }`.
- `hostPicture { windowId, itemId }`: a picture of the item's page as that window shows it (`tabs.captureVisibleTab`, JPEG, at most 1600 px wide), for its card in another Margin window, asked just before the Safari window leaves for that one. Only while the item's tagged tab is the one in front there. Answered `{ data }`: a `data:image/jpeg` URL, or null. Never stored or logged on either side; the app keeps it in memory while the card shows and sends it to that window's page alone (`pagePicture`).
- `goBack`, `goForward`, `reload { tabId }` (as above) for the tab of the item shown.
- `hostMedia { itemId, command, tabId? }`: the background mini player's button for the item's page (`background/hosted.ts` `media`): `command` `toggle`, `prev` or `next` is the page's (`content/media.ts` `mediaCommand`), `mute` the tab's (`tabs.update` muted). `tabId`: the tab the copy's `media` push named for the item, used only when the item's tag is gone and that tab is no other item's. Answered `{ ok }` (and `muted` for `mute`).
- **The preview card** (its wire names keep its first name, Peek, so an older copy and a newer app still talk; docs/PEEK-SPLIT.md §2; app/platforms/macos/shell/HostedPeek.swift, background/peek.ts, hosted.ts). Copy → app pushes, acted on by the session (never passed to a page): `peekOpen { id, url, source, tabId, notAfter }` (a page's click in a window the app hosts; `notAfter` in ms since 1970), `peekCancel { id }` (no answer came by `notAfter`: the page opened the link itself), `cardPage { url, title }` (the card's page now), `cardKey { key: 'close' | 'expand' }` (Esc or ⌘↩ in the card's page). App → copy: `peekAnswer { id, ok }` (at once; answered `true` while the click still waits, else `false`), `hostShow { windowId, itemId: 'peek-card', url, role: 'card', fresh? }` (the card's page in its window: that window is the card's from then; `fresh`: a new Peek, its tab sent there), `hostPromotePeek { fromItemId: 'peek-card', toWindowId, toItemId }` (Expand: the tab moved, a blank left behind), `hostCardClose {}` (its tab closed, a blank left so the window stays), `newWindow { url }` with an http(s) `url` (the card's window opened at its page; the app's ask only). The back and forward buttons are `goBack`/`goForward { windowId }` of the card's window.
- **The UI pushes** (copy → app, `push { windowId, msg }` for the window Margin hosts for that profile; any other window's: ignored). Margin.app passes on only the types in `app/platforms/macos/shell/UIPush.swift` `forwarded`, and of each only the fields listed there, checked and cut; the page gets `{ type, ...fields }` through `marginApp.receive`. A copy's tab becomes the UI's number for its item (an entry whose tab isn't an item open in Margin is dropped). Which Margin window: `HostedSession.copyPush` (DECISIONS.md, the mini player).
  - `media { sources: [{ tabId, itemId, url, title, subtitle, artwork, playing, muted, canPrev, canNext, updatedAt, pausedAt }] }`: the background mini player's sources in that window, playing ones first, the newest first, at most 8 (`background/media.ts`), sent when they change (and again for every window as the link comes). `artwork`: a PNG data URL the copy made from the page's Media Session artwork, or null. The page gets `tabId` (the UI's number), `title`, `subtitle`, `artwork`, `playing`, `muted`, `canPrev`, `canNext`, `updatedAt`, `pausedAt` (never `itemId` or `url`). Standing: a window that no longer gets it is sent `{ type: 'media', sources: [] }`.
  - `toast { text }`: a word in the theme's toast (at most 140 characters).

A split's cut panes (docs/PEEK-SPLIT.md §4b), Margin's own window only: the app pushes `{ type: 'paneCut', panes: { <item>: { window, left?, right?, up?, down? } } }` (each side present `"slide"`: a side its arrow slides into the pane; `{}` for none; also in the hello as `paneCut`) when it changes, and `{ type: 'paneHover', window }` (a cut pane's window, or `null`) as the pointer enters and leaves one (never per move). The page answers a press of an arrow with `perform` `split.slide { item, side }` (`left`, `right`, `up` or `down`, one of the pane's sides), which the app's engine does (`HostedSession.slidePane`).

Margin's own window's page (`host: 'app-window'`) also gets, from the app: `pageOutside` in its hello and `{ type: 'pageOutside', on }` when it changes (the window hosts another app's window beside it and is only the sidebar's tile: the UI lays out with no page area of its own, the sidebar docked: `ui/host-app.ts`), `pageHosted` in its hello and `{ type: 'pageHosted', on }` (a hosted window in its page area, under Margin's window: the sidebar docked, no launcher), `pageState` (`empty`, `loading` or `shown`; while Margin starts, `loading` with `pageStarting` / `starting: true`: the start screen over the whole window, and, held up, `pageStuck` / `stuck`: what's wrong in Margin's words, the page's `perform` `startup.retry` and `startup.skip` its two choices) and `pageOpening` (the name of what's opening, while `loading`) and `pageOpeningBundleId` in its hello and `{ type: 'pageState', state, label, bundleId? }` when they change (`bundleId`, only while `loading` and when known: the app whose icon the loader shows, the app's own or the hosted browser's for a web item (`com.apple.Safari`); the page looks the icon up in its `apps`, so no icon bytes travel with it) (the page card's state, put on the theme's root as `m-page-state`: `app/shared/ui/themes/README.md` "The page card's state"), `apps` in its hello and `{ type: 'apps', apps }` as overlays get them (above), and, the first time with an empty library, `{ type: 'command', name: 'edit-space', spaceId }` (the space the app made, opened in the UI's space editor for the person to name), and `marginPage` in its hello and `{ type: 'marginPage', page }` when it changes (`'settings'` or null: Margin's own page in the page area while nothing's hosted there, its Settings tab, a library item `margin://settings` with the target `{ kind: 'margin', page: 'settings' }`; the page draws it instead of the launcher: `settingsAsked`). The page's `openLauncher` is the app's (`HostedSession.openLauncher`): with `settings: true` (the palette's Settings, a theme's `settings.open`) the library's `openMarginPage` (the space's Settings item shown again, else a new one), else (Archive) the launcher in the page area, the item shown there parked. (Until 2026-11-20, `{ type: 'command', name: 'settings' }` opened the launcher's Settings in place; no longer sent.)

### User themes (the app's own data, to its overlays)

The themes the person imported belong to the Mac, not a profile: the app keeps them (margin-core's `data/themes.rs`, the Mac's through `app/platforms/macos/shell/ThemeStore.swift`; `~/Library/Application Support/Margin/themes/`: `<id>.json`, the stored package, and `index.json`). A copy gets only the index, never a package. `DECISIONS.md` "Margin 2, Phase 6: user themes".

- **To the copy:** `req userThemes { list }` (`link.ts APP_REQUESTS`) after each `snapshot` and whenever the index changes: `list` is `[{ id, name, version, author, bytes, savedAt }]`. The copy keeps `{ id, name, version, author }` of each in `storage.local` `userThemes`, so `updateSettings { theme }` and `updateThemeSettings` take an imported id.
- **To the overlays:** each hello has `themes` (the index), and every overlay gets `{ type: 'themes', list }` when it changes. Which package an overlay draws: the stored one when its profile's `settings.theme` is in the index, otherwise the copy's `theme` (a copy sends Arcadia for an id it doesn't ship). The same package is never pushed twice to one overlay.
- **What the overlay asks** (`perform`):
  - `theme.import`: the app shows `NSOpenPanel` (a folder or a `.margintheme` file, over a full-screen window), reads what was chosen within caps (a folder: regular files only, no links, two folders deep, 70 files, 512 KB each, 4 MB in all, hidden folders left out; a file: 4 MB) and pushes `{ type: 'themeFile', kind: 'folder', files: { path: base64 } }`, `{ type: 'themeFile', kind: 'zip', zip: base64 }` or `{ type: 'themeFile', error }` (Margin's words) to that overlay only. Cancelled: nothing. The overlay checks it (`ui/theme-import.ts`).
  - `theme.save { value }`: a package the overlay checked, as `ui/theme-loader.ts encodeStoredTheme` makes it. The app checks its shape, its id (the manifest's rule, not a built-in's, the same as the manifest's), its size (4.5 MB) and stores it; then the index goes out (above) and the overlay's copy is asked `updateSettings { patch: { theme: id } }` for that window. Refused: `{ type: 'themeSaved', ok: false, error }` to that overlay.
  - `theme.remove { id }`: gone from the store; every linked copy whose `settings.theme` is that id is asked `updateSettings { patch: { theme: 'arcadia' } }`; the index goes out, and overlays drawing it draw the copy's package again.
- **The log** says kinds and byte counts (`themes: a folder read for safari:P1#7 (81234 bytes)`), never a name, a path or content.
