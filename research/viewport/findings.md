## research:safari-dnr (`artifacts/r-dnr`)

No. Safari's declarativeNetRequest can rewrite request headers but not response headers, so no DNR rule can strip X-Frame-Options or CSP frame-ancestors in Safari. Safari 16.4 added "modifyHeaders" (Apple's release notes say only "Added support for the modifyHeaders action type"). MDN's compat data, which Apple reviewed, lists RuleAction.requestHeaders as Safari 16.4 and RuleAction.responseHeaders as unsupported. Current WebKit main (October 2026) matches that: the Safari rule parser accepts responseHeaders and its allowed-header list includes x-frame-options, content-security-policy and content-security-policy-report-only. It even passes them into the content-rule-list JSON as "response-headers". But WebCore's ModifyHeadersAction only has applyToRequest, and nothing ever reads responseHeaders except parse, serialize and hash. So these rules are accepted and then do nothing. The X-Frame-Options and frame-ancestors checks run in the network process against the raw network response, and content rule lists only ever change the outgoing request. Removing the headers therefore cannot allow framing in Safari, and Safari's webRequest only observes (it cannot block or rewrite). The only off switch is an internal WebKit preference (IgnoreIframeEmbeddingProtections) that extensions cannot set. On the plus side, measured in both WebKitGTK and Chromium: a same-origin shell frames pages that send X-Frame-Options SAMEORIGIN or frame-ancestors 'self' with no DNR at all. Only X-Frame-Options DENY and frame-ancestors 'none' (or lists that leave out the site itself) are blocked, so in Safari those sites need a fallback. In Chromium, which does support responseHeaders, a static rule {resourceTypes:[sub_frame], domainType:firstParty, remove XFO+CSP} makes the shell work and keeps direct third-party framing blocked. But it opens a measured hole: an attacker page can frame a frameable same-site page, which then frames the protected DENY page. A per-tab session rule (tabIds + requestDomains + initiatorDomains) closes that hole for other tabs. It must be removed when the shell tab navigates away (measured: while it stays installed, the hole reopens in that tab). Safari silently ignores tabIds (the parser drops unknown keys), so the per-tab rule would not be scoped there anyway. A non-DNR fallback was measured in WebKitGTK: fetch the page and document.write it into an about:blank iframe. This renders DENY and 'none' pages, keeps first-party cookies, gives the correct innerWidth, and allows history.replaceState to the real URL. But a nonce-based CSP inherited from the shell blocks the written page's scripts, and every navigation inside the frame would have to be emulated.

### Blockers

- Safari's declarativeNetRequest silently ignores responseHeaders operations. This holds for every Safari version per MDN BCD (Apple-reviewed) and for WebKit main as of October 2026, where WebCore has only ModifyHeadersAction::applyToRequest. So no rule can remove X-Frame-Options DENY or CSP frame-ancestors 'none'. In Safari, the iframe shell cannot show those sites through DNR.
- No other Safari extension API can rewrite response headers: webRequest only observes (WebExtensionAPIWebRequestEventCocoa.mm:82-85), and the only off switch (IgnoreIframeEmbeddingProtectionsEnabled) is an internal WebKit preference that extensions cannot set.
- Safari silently ignores the tabIds condition, so a rule cannot be limited to the shell's tab. Any header-relaxing rule would apply in every tab, even if Safari later supports responseHeaders.

### Mitigations

- Keep the shell for sites that are not DENY or 'none'. Same-origin framing passes X-Frame-Options SAMEORIGIN and frame-ancestors 'self' with no DNR (measured in WebKitGTK and Chromium).
- Detect blocked sites and fall back per origin. Either watch webRequest.onHeadersReceived with extraInfo ['responseHeaders'] (observation is supported in WebKit, WebExtensionAPIWebRequestCocoa.mm:340-352), or detect that the iframe never posts a ready message within N ms. Then use Margin's current non-iframe layout for that origin and remember the choice.
- Optional experimental fallback for DENY/'none' sites in Safari: fetch(url, {credentials:'include'}) and document.open/write the HTML into an about:blank iframe, then history.replaceState to the real URL. This was measured to work in WebKitGTK. But every navigation inside the frame must be intercepted (in-frame navigations hit the network and get blocked), reload breaks, and a nonce-based CSP inherited from the shell blocks scripts unless nonces are rewritten. Treat it as a last resort.
- Chrome build, if response-header stripping is wanted there: use a per-tab session rule, not a static one. {id: tabId, priority: 1, action: {type: 'modifyHeaders', responseHeaders: [{header: 'x-frame-options', operation: 'remove'}, {header: 'content-security-policy', operation: 'remove'}]}, condition: {tabIds: [tabId], resourceTypes: ['sub_frame'], domainType: 'firstParty', requestDomains: [host], initiatorDomains: [host]}}. Install it only while the shell is the tab's top document, and remove it on any top-level navigation (webNavigation.onBeforeNavigate with frameId 0) and when the tab closes.
- Back the Chrome rule with a content-script check in all frames at document_start. If the frame is one whose X-Frame-Options/CSP was stripped (known from webRequest observation), and its parent is not the top document or the top is not a same-origin Margin shell (reading top.location throws, or the shell marker is missing), blank the document. This closes the measured nested-frame clickjacking hole.
- Removing the whole content-security-policy header also removes XSS protection (script-src and so on). Appending a header cannot loosen frame-ancestors, because every CSP header is enforced. If this route is used in Chrome, consider stripping only X-Frame-Options and stripping CSP only when frame-ancestors is actually present.

## research:nav-framing (`artifacts/r-nav`)

Navigation control works for the same-origin iframe shell, but only on Safari 26.2 or later, and only if the shell owns session history itself. The usual replaceState address-bar sync is not good enough.

1. **Navigation API.** It ships in Safari 26.2 (macOS 26.2, Sequoia and Sonoma). It is stable and on by default in WebKit main (Cocoa/GTK/WPE). WebKitGTK 2.52.6 also has it on by default.

2. **Frame-busting.** A same-origin child can call top.location=, .href=, .replace(), window.open(url,'_top'), click an <a target=_top> or submit a <form target=_top> (GET or POST). Each one fires 'navigate' on the TOP window with cancelable=true, and preventDefault() stops it in both engines. This also works from an isolated-world content script. Without it, the shell reloads in a loop (23 reloads in about 6 s).
   - destination.url is the target URL.
   - sourceElement is the child's <a> or <form>.
   - formData is filled for POST only.
   - userInitiated is unreliable in WebKit: it is false even for a real XTest click.
   - For same-URL busts, navigationType is 'push' in WebKitGTK 2.52 and 'replace' in Chromium. Safari 27 changed this to 'replace'.
   - Navigations from cross-origin children do not fire 'navigate' on top.
   - Address-bar loads and reloads never fire 'navigate', so the shell cannot block the user.

3. **Navigations inside the frame.** For links, location.href/assign, window.open(_self), meta refresh and form GET/POST to another origin, the frame's own 'navigate' is cancelable, so the request can be forwarded to the top.
   - The TOP document's script must do the top-level navigation. WebKit throws SecurityError when a same-origin frame that loaded a third-party script and a third-party iframe, with no user interaction, navigates top cross-site.
   - POST bodies survive only if the form is rebuilt in the top document from e.formData.

4. **Server redirects.** The frame's 'navigate' only sees the same-origin URL before the redirect. The shell sees the frame load event, then contentWindow.location throws SecurityError and contentDocument is null.
   - Escape that worked in both engines: a document_start content script inside the cross-origin document calls window.stop() and posts its URL to the top, and the top navigates there.
   - In WebKitGTK the isolated user script even ran inside an X-Frame-Options-DENY error document. Chromium needs webNavigation.onErrorOccurred (ERR_BLOCKED_BY_RESPONSE) for that case.

5. **Session history.** Naive sync (iframe navigates, then top replaceState) handles live back/forward and title sync in both engines. But it writes the wrong per-entry URL/title into the back-forward list. After leaving the site and returning without bfcache, those entries go dead: the address bar changes but the page does not. 'Top-owned history' passed every case in both engines, with and without bfcache, and gave a clean back-forward list: the top calls pushState(dest), the iframe uses location.replace, and popstate leads to iframe.replace. SPA pushState inside the frame must be rewritten by a MAIN-world wrapper (verified in WebKitGTK).

6. **Framing the same URL.** WebKit allows it under X-Frame-Options SAMEORIGIN, CSP frame-ancestors 'self', an explicit own origin, and frame-ancestors 'self' combined with X-Frame-Options DENY. It is blocked by DENY alone, 'none', or a foreign host list. Both engines agree.

### Blockers

- Safari < 26.2 has no window.navigation, so there is no cancelable hook for frame-busting. The iframe-sandbox fallback leaks: top.location.replace() still navigated top in WebKitGTK 2.52 and caused a reload loop. On Safari < 26.2 the shell must be disabled, or limited to sites known not to bust, behind a reload-loop detector.
- Sites whose own pages send X-Frame-Options DENY, frame-ancestors 'none', or a frame-ancestors list without self cannot be loaded in the same-origin frame (verified in both engines). Navigation control cannot fix this; it depends on DNR header modification (other topic) or a per-site fallback to non-shell mode.
- Naive address-bar sync (replaceState after the iframe navigates) leaves dead back/forward entries once the page is restored without bfcache, in both engines. The shell must own session history: top pushState plus iframe location.replace, plus a MAIN-world rewrite of pushState inside the frame. That adds complexity and depends on MAIN-world content-script support in shipping Safari.

### Mitigations

- Gate the shell on `'navigation' in window` (Safari ≥ 26.2). Add a sessionStorage reload-loop detector: the same URL shelled N times within T seconds triggers a fallback to non-shell mode.
- Top content script (isolated world, document_start, top frame only) registers navigation.addEventListener('navigate'). Skip events that are sameDocument, not cancelable, or self-initiated (use an allow-flag or URL). For cross-document navigations to a destination same-origin with the shell, call preventDefault, then:
- If destination equals the frame's current URL, swallow it (frame-bust).
- Otherwise route it into the frame with history.pushState(dest) plus iframe.contentWindow.location.replace(dest).
Allow cross-origin destinations (they are real top-level navigations).
- Frame content script (isolated, all_frames, document_start; active only when window.name==='margin-frame' && parent===top) handles the frame's own 'navigate':
- Cross-origin destination: preventDefault and postMessage to the top. The TOP script navigates, which avoids WebKit's untrusted-iframe block. For POST, send e.formData entries and rebuild a <form method=post> in the top document.
- Same-origin cross-document GET: preventDefault and ask the top to do pushState plus iframe location.replace.
- Same-origin POST: allow natively and replaceState-sync as a fallback. This is a known limitation: that entry may die without bfcache.
- Do not rely on NavigateEvent.userInitiated in WebKit (false even for real clicks). If activation matters, track pointer/click events in the frame content script or check navigator.userActivation.isActive.
- Escape path for frames that end up cross-origin (server redirects, OAuth): at document_start in the cross-origin frame document, the content script calls window.stop() and posts {marginEscape: location.href} to the top. The top accepts it only when e.source === iframe.contentWindow (origin may be 'null' for XFO-blocked error docs) and sets location.href itself. Backups:
- Shell iframe 'load' plus a SecurityError check on contentWindow.location.
- Background webNavigation.onCommitted / onErrorOccurred for the shell's frameId, then tabs.update(tabId, {url}).
Cost: the redirect target is fetched twice.
- Address bar and title:
- Keep replaceState only as a fallback when the frame URL differs from the top URL.
- Mirror the frame's <title> with a MutationObserver (verified).
- Copy favicon and theme-color links (not tested).
- Tag each top history entry with the frame document id so popstate can pick same-document replay or iframe location.replace.
- MAIN-world document_start script in the frame (manifest world: MAIN, supported in WebKit source):
- Rewrite history.pushState into frame replaceState plus a top pushState.
- On top popstate within the same document, apply replaceState plus a synthetic PopStateEvent.
- Override window.self to return window.top, which defeats the OWASP display:none anti-framing pattern without a bust.
- Handle fragment-only pushes by cancelling the frame navigate and doing top pushState plus frame location.replace('#x') (untested).
- Expect WebKit's rate limiter (200 navigate events per 10 s per window) to cut off spammy busters. Re-attempt shell-initiated navigations after the window resets if they get aborted.
- For headers: same-origin framing already passes XFO SAMEORIGIN and frame-ancestors 'self'. Only DENY, 'none' or foreign lists need DNR responseHeaders removal on sub_frame requests (separate topic).

## research:shell-mechanics (`artifacts/r-shell`)

Yes. A document_start content script can take over the top-level document in time. Doing it cheaply needs a different shell than the leading hypothesis's iframe src=location.href. In WebKit, document_start content scripts are ordinary WebCore UserScripts. They run synchronously the moment the HTML parser creates <html>, before any page script runs, and nothing in current WebKit makes them wait. Safari's ~0.2s "injected" time is therefore network time before the document exists, not a late injection. Measured in both engines, the script ran 4–27ms after responseStart, and Margin's real Chrome build tracks TTFB exactly (injected = responseStart + 14–22ms). From the isolated world, window.stop(), document.open()+write, and swapping out document.documentElement each prevent every page script, in WebKitGTK 2.52 and in Chromium. replaceChildren() does nothing, because <html> is still empty at that point. The leading variant (stop the page, then load an iframe with src=location.href) costs one full extra TTFB on every page (+62ms at a 50ms TTFB, +214ms at 200ms). The HTTP cache did not avoid that second fetch, even with max-age. It also re-requests POST results as GET. In WebKit it is blocked outright by page CSPs whose frame-src/child-src/default-src lack 'self', and in both engines such CSPs also block every page-initiated navigation inside the frame. A better shell, measured end-to-end in WebKitGTK, is the "transplant". Swap the parser's <html> for Margin's shell, so the parser keeps filling a detached tree where nothing runs. When parsing ends, serialize that tree (Element.getHTML with its shadow roots) and document.write it into a same-origin srcdoc iframe. The frame then reports location.href equal to the page URL, inherits the page's CSP (nonces still match), runs the page's scripts in the same order as a normal load, and has the card's smaller viewport. Then turn every cross-document navigation of the frame into a top-level navigation through the Navigation API 'navigate' event, and re-submit POSTs at top level. This means no URL is ever fetched as a frame, so X-Frame-Options, frame-ancestors, frame-src and Sec-Fetch-Dest: iframe never come into play. It also avoids any double fetch and keeps POST working. A guard on the top window's navigate event stops frame-busting reload loops (127 reloads in about 3s without it, 1 with it). The costs: DOMContentLoaded +8–17ms on normal pages and about +93ms on a 1.2MB page; first paint waits for the whole HTML on pages that stream it; it needs the Navigation API (Safari 26.2+ per secondary sources); and some quirks remain (navigation.currentEntry.url stays about:srcdoc in WebKit; the frame's navigation timing is that of about:srcdoc). The frame's own content script can recognize Margin's frame by an expando set on the iframe element from the isolated world and read via window.frameElement. The page cannot see or fake it (it can fake attributes). Combine it with parent===top. Chromium needs a MAIN-world writer for the transplant, because isolated-world document.write puts the written page under the extension's CSP; WebKit has no per-world CSP.

### Blockers

- The leading variant (window.stop() + <iframe src=location.href>) is not workable as the general mechanism in Safari. WebKit blocks content-script-inserted iframes on pages whose CSP frame-src/child-src/default-src lacks 'self' (measured), unless a DNR rule strips the main_frame CSP for every site. Even then, the page's own in-frame navigations are blocked by the top document's frame-src in both engines. It also costs one full extra TTFB per page (the HTTP cache did not help) and re-requests POST results as GET.
- The transplant variant depends on the Navigation API 'navigate' event to turn frame navigations into top-level ones. Without it (Safari before ~26.2, unverified), uncaught frame navigations would be fetched as frames and run into XFO, frame-ancestors and frame-src again.
- Chromium only (the secondary dist/chrome build): isolated-world document.write runs the written page under the extension's isolated-world CSP, so a MAIN-world writer is required. That writer is blocked on pages enforcing Trusted Types; there the Chrome build would need the src variant or no shell.

### Mitigations

- Use the transplant shell (r-shell/shell-prototype.js). At document_start, swap the parser's <html> for the shell so the page never runs at top. On the shell's DOMContentLoaded, serialize the detached tree with Element.getHTML({shadowRoots}) and document.write it into a same-origin iframe whose srcdoc is set before insertion (no extra history entry, Navigation API enabled), then call history.replaceState in the frame.
- Intercept frame navigations on frame.contentWindow.navigation 'navigate': skip destination.sameDocument, hashChange and downloadRequest. Otherwise preventDefault and do location.assign at top (reload -> location.reload; formData -> re-submit as a top-level form POST, files via DataTransfer). No document is then ever fetched as a frame, which avoids XFO, frame-ancestors, frame-src, Sec-Fetch-Dest: iframe, double fetch and broken POSTs.
- Guard against frame-busting: on the top window's navigation 'navigate', cancel navigations that Margin did not start and whose destination equals location.href (and are not reloads).
- Put the takeover in a tiny first content-script file at document_start, before the ~120KB of UI scripts, and guard re-entrancy with a window flag (in WebKit, document.write'd <html> re-runs document_start scripts). Skip non-HTML documents (document.contentType) and any document whose <html> already has children (too late).
- Mirror title, favicon and theme-color from the detached <head> into the shell's <head> early, with a MutationObserver on the detached tree.
- Build shell DOM with CSSOM and adoptedStyleSheets, not style="" attributes; Chromium reported style-src violations for the shell's inline style attribute under a 'style-src self' page CSP.
- Recognize Margin's frame from the frame side with an isolated-world expando on the iframe element (window.frameElement.__marginShellFrame) plus window.parent === window.top. Attributes and window.name can be faked by the site.
- Do NOT add a DNR 'script-src none' CSP to main_frame: document_start already always wins, and an inherited CSP would kill the transplanted page. Use DNR CSP/XFO edits only if the src variant is kept as a fallback.
- Give the shell iframe delegation through its allow attribute (fullscreen, autoplay, picture-in-picture, payment, clipboard-read/write, camera, microphone, geolocation, display-capture, publickey-credentials-get/create, web-share) and allowfullscreen, or those features will fail inside the frame.
- Add nav.responseStart to Margin's '[margin] timing' debug line (extension/content/sidebar.js logTiming) to confirm in Safari that 'injected' is TTFB-bound.
- Later optimization: progressive transplant (write completed body children as they arrive) to recover progressive rendering on pages that stream their HTML. Show Margin's loading pill until the transplant in the meantime.

## research:feature-parity (`artifacts/r-parity`)

Most web-platform features keep working in a same-origin child frame. WebKit's subframe gates (Permissions Policy default 'self', "same origin as top document" for Notification/Push, "same origin with ancestors" for WebAuthn create, the Apple Pay ancestor checks) are all satisfied when the frame's origin equals the top document's. I confirmed this in WebKitGTK 2.52.6 for notifications, geolocation, camera/mic, screen capture, clipboard read/write, element fullscreen, wake lock, window.open, downloads, beforeunload, find-in-page, page zoom, and all storage: cookies of every SameSite kind, localStorage, sessionStorage, IndexedDB, service-worker control and hasStorageAccess. Storage results were the same with ITP on and third-party cookies blocked.

Several things need the shell's help:
- **Keyboard focus:** Space and arrow keys don't scroll, and Select All selects the sidebar, until the shell calls iframe.contentWindow.focus(). WebKit allows that call without a user gesture for same-origin frames.
- **Title, theme-color, favicon:** Safari reads these from the top document only. The shell must mirror them, and favicon links must be copied before the shell's own load event, because WebKit loads icons once, at main-document load, and only for the main frame.
- **URL, Share, History:** these need history.replaceState kept in sync with the iframe.

Some things degrade or break:
- **Loading indicator:** Safari's progress bar and stop button are dead for navigations inside the iframe (progress is reported for the main frame only; measured isLoading=false, progress 1.0).
- **Printing:** printing the main frame gives the sidebar plus one clipped viewport (1 page instead of 6). It needs ⌘P interception that calls iframe.contentWindow.print(), plus a fallback.
- **Hide Distracting Items:** WebKit resolves any target inside a subframe to the `<iframe>` element itself.
- **Reader:** likely unavailable (unverified).
- **Other Safari extensions:** their content scripts default to top-frame-only, and scripting.executeScript defaults to the main frame, so they would act on the shell instead of the page.
- **Popups:** a shelled popup's page sees window.opener === null and window.close() does nothing (measured).
- **Reload after a POST:** it becomes a GET.
- **Referer and document.referrer:** they become the shell's URL.
- **Double request:** every page is fetched twice, so one-time URLs (OAuth callbacks, magic links) are at risk. Because the iframe request is same-site, SameSite=Strict cookies are sent even when the user arrived from another site (measured).

Unverified on Safari: password AutoFill and passkey autofill in same-origin frames (likely fine), and webpage translation (WebKit has an includeSubframes option since macOS 14).

### Blockers

- The double request is a correctness break, not just cost: every top-level GET is fetched twice (measured: /shell then /page). Single-use URLs (OAuth/OIDC callbacks with a code, magic-login and email-verification links, password-reset tokens, one-time downloads, payment return URLs) can fail or fire twice unless the shell avoids re-requesting or skips such pages. Because the second request is same-site, SameSite=Strict cookies are sent even after a cross-site arrival.
- Shelled popups break OAuth/SSO/payment popups (window.opener is null inside the iframe; window.close() is a no-op from a subframe). The shell must never run in script-opened popups.
- No extension-side fix exists for: Safari Reader (likely), Hide Distracting Items (main-document only), menu-driven File > Print / Export as PDF (prints the main frame unless ⌘P is intercepted), and other Safari extensions whose content scripts or executeScript target only the top frame. A per-tab 'show without Margin' escape hatch is needed for these.
- Safari's loading UI (progress bar, stop button) is dead for every navigation inside the iframe; Margin must supply its own.

### Mitigations

- Create the iframe with allowfullscreen and allow="fullscreen; payment; camera; microphone; geolocation; display-capture; web-share; screen-wake-lock; publickey-credentials-get; clipboard-read; clipboard-write; autoplay; picture-in-picture". The same-origin defaults already allow most of these, so it is belt-and-braces.
- Focus: call iframe.contentWindow.focus() after every iframe load, and give focus back to the iframe after sidebar interactions. WebKit allows this without a gesture for same-origin frames, and it does not steal focus from Safari's address bar. Register Margin's own keyboard shortcuts on the iframe's window too.
- Mirror the browser chrome into the shell: document.title via a MutationObserver on the iframe's <title>; <meta name=theme-color> (including media variants and live changes); <link rel=icon / apple-touch-icon / manifest>. Copy icons on the iframe's DOMContentLoaded or load, before the shell's load event, because WebKit loads favicons only once, at main-document load.
- Sync the URL with history.replaceState(iframe URL) after each iframe navigation, including pushState inside the iframe. This drives the address bar, Share, bookmarks and Handoff, and calls WebKit's updateGlobalHistory so Safari History gets entries. Set the title before or alongside.
- Draw Margin's own progress bar for iframe navigations (beforeunload/pagehide in the iframe through its load event); Safari will not show one.
- Printing: listen for keydown ⌘P in the iframe window, preventDefault, then call iframe.contentWindow.print(), which reaches Safari's printFrame delegate with the iframe's frame. As a fallback for menu-initiated printing, on beforeprint in the shell hide the sidebar, make the iframe static and expand it to contentDocument scrollHeight (measured: all content printed; pagination imperfect). Restore on afterprint.
- Skip the shell when: window.opener is non-null (popups); the document is a POST result (idea, untested: DNR rule {resourceTypes:['main_frame'], requestMethods:['post']} adding a Server-Timing marker read via performance.getEntriesByType('navigation')[0].serverTiming); the page is non-HTML (PDF/image/media document); and URL patterns for single-use tokens (OAuth callback ?code=&state=, magic links) unless the top response can be reused without a second request.
- Offer a one-click per-tab or per-site 'show without Margin' toggle (fall back to today's overlay sidebar) for Reader, Hide Distracting Items, menu Print / Export as PDF, and other extensions that act only on the top frame.
- Referrer: optionally add a DNR session rule (condition: sub_frame request to that URL, initiated by the same origin) that sets the 'referer' request header to the original document.referrer. 'referer' is on WebKit's DNR header allowlist; document.referrer inside the iframe stays the shell's URL.
- Paint the shell's top edge in the page's theme-color, or copy theme-color, so Safari's sampled top colour and edge effects look like the page rather than Margin's chrome.
- Optional: counter-scale the sidebar when devicePixelRatio changes (page zoom also zooms the shell UI).

## research:prevalence-security (`artifacts/r-sec`)

Prevalence: by the Web Almanac 2025, X-Frame-Options (XFO) headers are 72% SAMEORIGIN and 24.6% DENY. XFO appears on about 30% of all sites and 67% of the top 1,000. CSP is on 21.9% of sites, and about half of those policies use frame-ancestors. The single most common CSP value, at 18-20% of CSP headers, is "block-all-mixed-content; frame-ancestors 'none'; upgrade-insecure-requests". A same-origin shell needs no header changes for SAMEORIGIN and frame-ancestors 'self'. Only DENY (roughly 7-9% of all sites, more among top sites) and frame-ancestors 'none' (at least about 4% of sites) block it. I measured gist.github.com, pypi.org and bitbucket.org (DENY plus 'none') and accounts.google.com (DENY). The proxy blocked most of the big sites on the list, so their headers are not measured. I found a second blocker that is not in the brief. The site's own top-level CSP (frame-src, child-src or default-src without 'self', for example pypi.org frame-src 'none') blocks an iframe made by an isolated-world content script in WebKitGTK. Chromium lets content-script iframes bypass page CSP, so Chromium E2E tests would give false passes. Security: Safari's DNR cannot scope a rule to "frames this shell made". From WebKit source plus WebKitGTK probes: domainType firstParty is measured against the top document, not the initiator. initiatorDomains becomes if-frame-url, which matches the frame's current document (about:blank on its first load). tabIds is silently ignored. So a "remove XFO, firstParty" rule would also strip XFO from victim pages nested in ad or widget frames on the victim's own pages, and when a same-site subdomain is the top page. I reproduced the subdomain case in Chromium. Removing or setting CSP wipes the whole policy (measured: the blocked inline script then ran), and 'append' cannot relax frame-ancestors (measured). Safest design: never remove headers. Use DNR 'set' X-Frame-Options: SAMEORIGIN on sub_frame responses of the shelled host only. WebKit's own SAMEORIGIN check (same origin as top AND all ancestors) then does the scoping, whatever the DNR conditions mean. Only same-origin documents gain anything, and they already have full script access. Measured in Chromium: the shell loads DENY pages and all attack scenarios stay blocked. Fall back to push mode for frame-ancestors 'none'. Optionally replace the top document's CSP with a stricter Margin shell policy (script-src 'none'; frame-src 'self' ...). That stops the site's scripts in the outer document and blocks cross-origin navigations in the frame, so no URL-bar spoofing. Big caveat: open-source WebKit main only applies modify-headers to requests (applyToRequest). WebKitGTK applied no header changes at all. So whether shipping Safari modifies response headers must be confirmed, or no header-based unblocking is possible. App Store: Apple's guidelines say nothing specific, and WebKit's DNR allowlist explicitly includes x-frame-options and content-security-policy. Mozilla's add-on policy forbids relaxing security headers. Chrome Web Store hosts XFO/CSP-stripping extensions (per search results, unverified). A narrow DENY-to-SAMEORIGIN rewrite, disclosed in the listing, is the most defensible.

### Blockers

- Possibly fatal for header-based unblocking: open-source WebKit main applies DNR modifyHeaders only to requests (ModifyHeadersAction::applyToRequest; no response path found). WebKitGTK applied no header changes at all. If shipping Safari also ignores responseHeaders, no XFO or CSP rewrite is possible. The shell then works only on sites without XFO DENY, without frame-ancestors 'none' or a list lacking 'self', and whose top-level CSP allows 'self' frames. Everything else must use push mode. Needs confirmation (r-dnr topic / real Safari).
- Top-level page CSP (frame-src, child-src or default-src without 'self') blocks the shell's own iframe in WebKit, whatever frame-ancestors says (WebKitGTK measured: pypi.org-style frame-src 'none'). The only way around it is modifying the main_frame CSP, which depends on the item above. Chromium E2E cannot catch this, because content-script iframes bypass page CSP there.
- Safari DNR cannot express 'only frames created by this shell / only this tab': tabIds is silently ignored, initiatorDomains maps to the frame's current document (about:blank on first load), and domainType is top-relative. Any 'remove X-Frame-Options' rule therefore leaks to same-site subdomain tops and to victim pages nested in third-party frames, which is a real clickjacking regression. Use SAMEORIGIN rewriting instead of removal.
- Every top-level navigation is fetched twice (top + iframe). That replays non-idempotent GETs (one-time tokens, OAuth code callbacks, magic links). POST results cannot be re-requested at all, so those pages must not be shelled.

### Mitigations

- Never remove X-Frame-Options and never touch sub_frame CSP. While a shell for host H exists, add one session rule: action modifyHeaders responseHeaders [{header:'x-frame-options', operation:'set', value:'SAMEORIGIN'}], condition {resourceTypes:['sub_frame'], requestDomains:[H] (or urlFilter '|https://H/'), domainType:'firstParty', requestMethods:['get']}. WebKit's own SAMEORIGIN check (same origin as top and all ancestors) makes it safe even with Safari's loose conditions and ignored tabIds. Only same-origin documents gain framing, and they already have full DOM access. Remove the rule when the last shell tab for H closes.
- Sites with CSP frame-ancestors 'none' or an origin list without 'self' (including DENY + 'none' combos like github, pypi, bitbucket): don't rewrite CSP. Detect the failure (the iframe load throws SecurityError on contentWindow.location, or the frame content script never says hello) and fall back to the current push mode. Cache the decision per host.
- Optional, only if Safari applies response-header rewrites: 'set' the top document's CSP to a Margin shell policy on main_frame GETs for shelled hosts: "script-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-src 'self'; upgrade-insecure-requests". This lifts the site's own frame-src block on the shell iframe and stops the site's scripts in the outer document (no double execution). It is strictly tighter for script execution than any site policy. Exclude hosts that fell back to push mode, and non-GET requests.
- Navigation guard: always give the shell document frame-src 'self' (a <meta> CSP the content script inserts, measured to work in both engines, or the main_frame policy above). Cross-origin content can then never render under the site's address-bar URL. On violation, navigate the tab top-level. blockedURI is origin-only, so the frame's content script should report the exact target URL, or use tabs.update from the background.
- Sync the URL and title between frame and shell over extension messaging, checking sender.frameId and sender.url in the background. Don't use window.postMessage, which the page can forge. Sync on every same-origin frame navigation (replaceState) so the address-bar path is never stale.
- Limit replay risk: requestMethods:['get'] on the main_frame rule. Don't shell URLs with one-time-token patterns (code=, token=, ticket=, otp=, magic-link paths). Keep the shell persistent so later navigations happen only inside the frame.
- Test the security-relevant paths in WebKit, not only Chromium. Chromium's initiator-relative domainType hides the Safari nesting issue, and its content-script CSP bypass hides top-level frame-src blocks.
- App Store: describe it as 'lets a site frame itself only (DENY becomes SAMEORIGIN); never removes or weakens a site's Content-Security-Policy; never allows another site to embed it'. Add a per-site and a global off switch, and keep DNR scoped to the active host.

## research:alternatives (`artifacts/r-alt`)

Short answer: inside a Safari Web Extension, a nested browsing context (an iframe shell) is still the only way to give a page a genuinely smaller viewport and still have an interactive sidebar beside it, including in full screen. Every other candidate is either missing from shipping Safari, reserved for the embedding app, or unable to host UI.

(1) The extension sidebar API (sidebarAction/sidePanel) does not ship. WebKit main (2026-10-24) still compiles it out: ENABLE_WK_WEB_EXTENSIONS_SIDEBAR is '0 && ...'. Its runtime pref is 'testable' and off by default, which means test infrastructure only, not even Safari Technology Preview. Safari release notes 17.0 through 27.0 never mention it, and MDN BCD lists Safari as false. Apple is still working on it (a Left/Right side enum marked WK_MAC_TBA), so it is a future option only.

(2) These are all dead ends:
- meta viewport is ignored on macOS (UNUSED_PARAM in WebPage.cpp).
- the @viewport rule is dropped.
- tabs.setZoom is whole-page zoom.
- windows.update with a frame forces the window to the Normal state, which leaves full screen.
- Responsive Design Mode, _setFixedLayoutSize and the new WKWebView.obscuredContentInsets (macOS 26) belong to the embedder or Web Inspector. obscuredContentInsets is exactly the right primitive ('shrink the bounds of the layout viewport') but only Safari.app can set it.

(3) Docking Web Inspector to the left with a devtools panel does narrow the page. It is not viable: the minimum dock width is 500px, the user must open it by hand in every tab, and no extension API opens it.

(4) New candidate the team had missed: a custom root scrollbar gutter (html{overflow-y:scroll;direction:rtl} body{direction:ltr} ::-webkit-scrollbar{width:W}). Measured in WebKitGTK, it shrinks clientWidth, visualViewport, the fixed containing block, % widths and media queries (WebKit evaluates MQ width against the scrollbar-excluded layoutWidth). innerWidth and 100vw do not change. It is ruled out because the gutter is a scrollbar: page content, including top-layer elements, is clipped at its edge, elementFromPoint returns null there, and clicks scroll the page.

(5) A useful variant of the shell, measured identically in WebKitGTK 2.52 and Chromium: create an about:blank iframe, fetch the same URL from the shell, then call iframe.contentDocument.open()/write(). Under X-Frame-Options DENY plus frame-ancestors 'none', iframe src, <object> and <embed> were all blocked, but this path loaded the page. The frame's URL became the page URL, innerWidth was 700, cookies were present, scripts ran and pushState worked. It has three measured costs:
- the frame inherits the shell's CSP, so nonce scripts are blocked unless the nonces are rewritten (rewriting worked).
- a real link navigation inside the frame is still blocked, so navigations must be intercepted (Navigation API, Safari 26.2+) or the headers stripped.
- calling document.open again in the same realm throws "Can't create duplicate variable", so every navigation needs a fresh iframe.

(6) Prior art. Both open-source Safari App Store vertical-tab extensions push the page with margins, which breaks in the same ways as Margin today. DigitalN's Side Tabs uses a native app with Accessibility, and even it can only overlay in full screen. Apache Ripple's Chrome extension is a direct precedent for the same-origin self-iframe shell: at document_start it calls document.open/write on the top page and loads document.URL in an iframe.

Ranking of what remains viable:
1. Iframe shell, with framing restrictions handled by DNR header stripping where Safari allows it, or by the document.open variant with fresh iframes per navigation and nonce rewriting.
2. Current overlay/push mode as the fallback for sites the shell cannot handle.

### Blockers

- None of the alternatives to the iframe shell is viable inside a Safari Web Extension today, so the decision rests entirely on the shell's open problems (framing headers, navigation, CSP nonces, Safari features inside frames).
- For the document.open variant: sites with strict nonce CSP need nonce rewriting, and every real navigation must be intercepted or have its headers stripped, otherwise XFO/frame-ancestors block the next page load inside the frame.

### Mitigations

- Rank 1: iframe shell. Load pages with a plain iframe src where framing is allowed (or where DNR modifyHeaders can strip XFO/CSP in Safari). Fall back to the document.open variant: fresh about:blank iframe, fetch the same URL with credentials, open/write/close, rewrite script nonces to the shell's nonce, and use one new iframe per navigation.
- Intercept same-origin navigations inside the frame with the Navigation API (Safari 26.2+) or click/submit capture and route them through the shell. Send cross-origin navigations, SSO redirects and POST results that can't be re-fetched to a top-level navigation.
- Rank 2: keep today's overlay/push mode as a per-site fallback (denylist) for sites the shell can't handle; this is how every App Store vertical-tab extension works.
- Rank 3 (future): file Apple Feedback asking Safari to ship sidebarAction/sidePanel, or to let an extension reserve an edge inset (obscuredContentInsets-style). Recheck WebExtensionSidebarEnabled status and ENABLE_WK_WEB_EXTENSIONS_SIDEBAR in WebKit each Safari release.
- Don't pursue: meta viewport, @viewport, tabs.setZoom, windows.update bounds, the Web Inspector dock, or the custom-scrollbar gutter (the gutter narrows the page but can't host UI).

- Does Safari's DNR modifyHeaders actually strip X-Frame-Options and Content-Security-Policy on sub_frame responses in shipping Safari, and from which version?
- Do password AutoFill, passkeys, Reader, Translate, Find in page, printing and Apple Pay work in a same-origin iframe whose document was written with document.open, compared with a normally navigated iframe?
- How do servers and CDNs (Cloudflare challenge pages, Rails/Turbo, Accept-dependent endpoints) respond to the shell's fetch (Sec-Fetch-Dest: empty, Mode: cors) instead of a navigation request? Do service-worker-driven sites behave correctly?
- Does Safari on macOS really put the root ::-webkit-scrollbar on the left for direction:rtl and keep the custom (non-overlay) gutter when the system uses overlay scrollbars? This is academic, since the gutter can't host UI.
- Will a future Safari ship sidebarAction/sidePanel with WebExtensionSidebarEnabled at preview or stable status, and would its sidebar pane narrow the page or overlay it?

## proto-chromium (`artifacts/p-chromium`)

I built the same-origin iframe shell as a real MV3 extension and ran all of T1-T10 in Chromium, plus three extra checks (T11 reload, T12 print, T13 fullscreen). Everything is in artifacts/p-chromium/.

How the prototype works:
- **Takeover (shell.js, top frame only, document_start):** it runs `document.open()/write()/close()` and then `window.stop()` (ext/shell.js:52-55). It then builds a 260px sidebar and the card iframe (left 260, top/right/bottom 8, radius 6.25px, `src` = current URL). In the frame, frame.js picks out the card by an isolated-world expando, `frame.__marginFrame` (shell.js:87).
- **Sync:** the shell copies the card's URL (`history.replaceState`), title, favicon and theme-color to the top whenever frame.js reports a change.
- **Top navigations:** the shell's Navigation API `navigate` listener cancels same-origin top navigations (frame busting, `target=_top`, `top.location='/x'`). Non-bust ones are loaded in the card instead (shell.js:195-240).
- **Cross-origin from the card:** frame.js sends these to the top level (frame.js:58). POSTs are re-submitted from the top document. A cross-origin page that lands in the card after a redirect posts `xo-frame` to the shell, which hands it to the top with `location.replace`.
- **Blocked frames:** if the card ends up unreadable (blocked by XFO or CSP), the shell reloads the page top-level without the shell, marked so it does not shell it again.
- **Skipped pages:** popups that have an opener, top-level POST responses (a DNR rule adds a `Server-Timing` marker that the shell reads) and opaque-origin documents (CSP `sandbox`) are never shelled.
- **Header removal, three variants compared:** a static ruleset (sub_frame + firstParty, removes XFO and CSP), a per-tab session rule (`tabIds` + `requestDomains` + `initiatorDomains`), and the same per-tab rule removing XFO only with the fallback for CSP.

Results:
- **Works in Chromium:** viewport behaves like a 732px window (T1); cookies and storage are shared (T2); same-origin navigation and sync (T3); history (T4); cross-origin hand-off, including 302 redirects and POST (T5); frame-busting blocked (T6); per-tab rule and fallback (T7); keyboard focus handoff (T9); link targets and popups (T10); fullscreen (T13).
- **Unexpected Chromium finding:** calling `window.stop()` alone at document_start means the top document never renders, headless or headful: no requestAnimationFrame, screenshots hang. Doing `document.open()` first and `window.stop()` after fixes it. The shell then paints at about 24-39ms, the duplicate top-level download is aborted, and page scripts never run.
- **Costs and side effects found:**
  - Every top-level entry fetches the HTML twice, adding about one extra server response time.
  - SameSite=Strict cookies are now sent when the user arrives from another site.
  - The page's referrer becomes its own URL.
  - Browser print gives 1 page instead of 4.
  - Chrome's back-button list shows the last synced URL on every history entry.
  - CSP `sandbox` caused a reload loop until I added a guard.
- **Header removal:** the static firstParty rule is too broad. A same-site page on another origin, in another tab, could frame an X-Frame-Options DENY page. Removing CSP also strips the page's `script-src` protection inside the card.
- **Safari: header removal would not work.** WebKit main reads DNR `responseHeaders` but never applies them; only request-header changes are applied (ContentExtensionsBackend.cpp:486-489). In WebKitGTK the rule compiled but had no effect on X-Frame-Options or CSP. So in Safari, pages that forbid framing can only fall back to showing without the shell.

### Design notes

- Taking over the document in Chromium: at document_start call document.open(); document.write('<!doctype html><html><head></head><body></body></html>'); document.close(), THEN window.stop() (ext/shell.js:52-55). Never call window.stop() first or alone: the top document never renders (rAF never fires; screenshots time out, headless and headful; T8 'stop' renders nnnnn). The 'swap' approach (replace the parser's <html>) keeps downloading the whole response and delays the first frame until the page's body arrives (455ms vs 24-39ms in the 20MB streaming test).
- Load the card with frame.src set before inserting the iframe (no extra about:blank history entry). Mark it with an isolated-world expando (frame.__marginFrame = true) that frame.js checks through window.frameElement. Page scripts cannot see or copy it.
- Use the Navigation API navigate event on the TOP window. Ignore sameDocument and Margin's own navigations. Allow cross-origin, traverse and uncancelable ones. For same-origin push/replace: if the destination equals the card URL it is a bust, so drop it; otherwise load it in the card. A script reload while the card is still loading is a bust; otherwise turn it into a card reload. This took bust loops from 29-43 top reloads per 2s to 1, and handled target=_top in place (T6, T10). After a blocked bust, un-hide the card's html/body if they are display:none (OWASP pattern).
- Frame side (frame.js at document_start, all_frames): handle the navigate event for cross-origin http(s) destinations. Call preventDefault, then top.location.assign(url). For e.formData, rebuild the form in the top document and submit it; this keeps the POST body (T5e). Leave mailto:/custom schemes and downloads to the browser.
- Server redirects that land a cross-origin page in the card: frame.js in that page posts {__margin:'xo-frame'} to parent. The shell checks e.source === card and that the card really is unreadable, acks so the page calls window.stop(), and calls location.replace(url). replace (not assign) means Back returns to the previous page with no loop (T5c).
- Sync (ext/shell.js sync()): history.replaceState(history.state, '', cardURL), document.title, rel=icon and theme-color. Trigger it from frame.js events (start, dcl, navigatesuccess, currententrychange, pageshow, hashchange, title MutationObserver), and always re-read the values from the same-origin card rather than trusting message contents. Link click to synced took 150-161ms including the fetch.
- Fallback: if the card is unreadable at load and no hand-off message came within 50ms, store the URL in sessionStorage 'margin:noshell' and location.replace(url). The next document_start sees the flag and does not shell. Make it loop-proof: skip when self.origin === 'null' (CSP sandbox looped before this guard) and never navigate if sessionStorage throws. Remember failing origins so they skip the 3-fetch cost next time.
- Do not shell: popups with window.opener (OAuth flows need opener to be the page's window; T10 proved opener === card when unshelled), non-HTML documents, top-level POST responses, or opaque-origin documents.
- Header removal in Chromium: do not ship the static sub_frame + firstParty rule. It lets any same-site page on another origin, in any tab, frame DENY pages, and removing CSP wipes the page's script-src protection. Prefer a session rule per tab, armed before setting src (0.5-6ms), that removes only X-Frame-Options, with the fallback for frame-ancestors 'none'. Note that requestDomains/initiatorDomains ignore ports. Plan on Safari having no header removal at all.
- Focus: after card DOMContentLoaded call frame.contentWindow.focus(), and do the same after pointerup on non-input parts of the sidebar. Without it Space/Arrow do nothing (0px vs 497px). Margin's keyboard shortcuts must also be listened for inside the card (frame.js), since keys go to the focused frame.
- Fullscreen works with allow='fullscreen' on the iframe: the card fills the whole window over the sidebar (T13). Printing needs Cmd+P routed to card.contentWindow.print().
- Testing note: with any window.stop()-based takeover, Playwright page.goto(waitUntil:'load') never resolves because the top's DOMContentLoaded/load never fire after window.stop(). Wait for the card frame's readyState instead (lib.mjs gotoShell). Chromium still reports frameStoppedLoading for the top, so the tab spinner follows the card's load.
