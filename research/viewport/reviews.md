## verify:ux-parity: overall **sound-with-fixes**

My assigned step, the adversarial UX-parity review, is complete. I cannot answer the relayed user question 'why did you stop it' from inside this step; the agent that launched me has to answer it.

Bottom line: the transplant still gives a true narrower viewport, and nothing I found refutes the architecture itself. But it overstates parity. Under this lens I measured 9 regressions in WebKitGTK 2.52 that the recommendation either misses or rates as unverified or minor:
- an empty-card flash, or a frozen old page, on navigations with slow or streaming loads;
- scroll position lost on every reload and on Back without the back-forward cache;
- typed form fields lost on Back without the cache;
- Navigation-API SPAs turned into full reloads;
- 'Leave page?' asked twice;
- page-URL-keyed content-blocker hiding rules not applied in the card;
- text-fragment links ignored;
- window.close() doing nothing;
- legacy encodings turned into mojibake.

In addition, the password-save hook never fires for the user's real form (WebKit source plus a GTK signal trace).

Most of these are fixable with extra code: paint hold, scroll persistence, close() forwarding, an encoding skip, typed form rebuild, and modifier-aware click routing. Some are not: progressive rendering on streaming pages, form-state restore, Reader, top-only extensions, and window.top checks. Several of the issues are visible on every page load, which is how the fit layer got rejected ('doesn't work properly'), so the M-shell plan should add these fixes before Tirth tries it.

My prototype vshell.js follows the recommended design: isolated-world takeover, random frame name, srcdoc, adoptedStyleSheets, a frame-side navigate router at document_start, POST rebuild, the bust guard, and the main-wrap5 history wrapper. None of this was run on real Safari.

### Refuted or corrected

- **known_losses: password AutoFill and save inside the card is 'MEDIUM (unverified) ... the WebKit gates pass'.**: For saving passwords, the WebKit hook does not pass. Margin cancels the user's real form submission at the navigate event, and that happens before WebKit reaches dispatchWillSubmitForm, the will-submit-form hook that password managers rely on. The hook then fires only for the synthetic form Margin rebuilds in the shell. If that form uses hidden inputs, it exposes zero text fields, because WebKit only collects inputs where isTextField() is true. The design says 'rebuild <form method=post enctype=...>' and does not say which input types to use.  
  Evidence: Source: r-shell/wk/Source_WebCore_loader_FrameLoader.cpp:3976 dispatches navigate for POST before the policy check. For GET and links, the pending navigate event runs at 4520-4523, then dispatchWillSubmitForm at 4607; a cancelled navigate returns before 4607. v-ux-parity/src/Source_WebCore_html_HTMLFormElement.cpp:361-368 (textFieldValues keeps only isTextField inputs). Measured in WebKitGTK 2.52 (v-ux-parity/results.jsonl 'login-post'). Unshelled: one submit-form signal with [username, password]. Shelled: the frame's form produced no submit-form at all, and only the shell's rebuilt form fired one. With the hidden-input rebuild the field list was empty (PyGObject crashed on the NULL arrays). With a rebuild that copies the original input types, it showed [username, password]. Whether Safari offers 'Save password' for a script-submitted form in the top document is unverified.
- **Native session history: 'back, forward and leave-and-return all work with and without the back-forward cache' (what_works; key claim 5).**: The URL and title of each entry are correct, but page state is not. Without the back-forward cache, the card loses its scroll position and anything typed into form fields. On reload (Cmd-R) the scroll position is lost even with the cache on. In the design, history.state.__scroll is only written on hash-link pushes (3b), and nothing restores form state. WebKit never puts HTTPS pages sent with Cache-Control: no-store into the back-forward cache, so this hits logged-in sites (mail, banks, dashboards) every time. Session restore after relaunching Safari takes the same reload path; that case was not measured.  
  Evidence: Measured (results.jsonl 'restore'). Unshelled, page cache off: scrollY 3000 and both typed fields restored after Back; scrollY 3000 kept after reload. Shelled, page cache off: scrollY 0 and empty fields after Back; scrollY 0 after reload. Shelled, page cache on: Back restores, reload still gives 0. v-ux-parity/src/BackForwardCache.cpp:156-159 (HTTPS + no-store main frame is never cached).
- **risks: 'whether paint-holding during navigations causes an empty-card flash' is unknown; known_losses rates the first-paint delay MEDIUM.**: It does cause one, measured on screen. WebKit lets the new page paint (it stops holding the old one) once the top document looks non-empty, and that check only looks at the shell document and the shell's own loads, not the card. A shell holding a real sidebar passes the check right away, so the old page is replaced by an empty card. The card stays empty until the whole HTML has arrived and the card's render-blocking CSS has loaded. Unshelled pages either keep showing the previous page or render progressively. A mitigation (keep the shell visibility:hidden until the card's stylesheets have loaded) removes the blank card, but on streaming pages the old page then stays frozen for the whole HTML download. So on any slow or streaming load, a navigation either flashes an empty card or freezes on the old page; only near-instant loads avoid both.  
  Evidence: On-screen capture: Gdk.pixbuf_get_from_window on a real X window, sampled every 40 ms (results.jsonl 'flash'). 1.5 s streaming gap: unshelled showed the new page at 44 ms; shelled with a 30-line sidebar showed an empty card from 45 to 1558-1581 ms. Slow CSS (800 ms): unshelled kept the old page until 829-835 ms with no blank; shelled was blank from 44 to 874-901 ms, and still blank from 45 to 883 ms with no sidebar text. Shell hidden until the card's CSS loads: no blank, switch at 871-872 ms, but the 1.5 s streaming case froze until 1551-1554 ms instead of 44 ms. Source: LocalFrameView.cpp:6222-6290 (src copy); WebLocalFrameLoaderClient.cpp:840-851; WebPage.cpp:5047-5084 (freeze and unfreeze on page transition; shared WebProcess code). Black #000000 samples in a few runs, unshelled ones included, are capture glitches and were ignored.
- **known_losses MEDIUM: navigation.currentEntry staying about:srcdoc 'can confuse SPAs built on the Navigation API'.**: The real effect is worse. frame.js registers its navigate listener at document_start, before the page's, and calls preventDefault. The page's own navigate.intercept() then throws, so every in-app navigation in a Navigation-API router becomes a full top-level page load, and the app loses its in-memory state.  
  Evidence: v-ux-parity/src/Source_WebCore_page_NavigateEvent.cpp:107-108 ('Event was already canceled'). Measured ('navapi-intercept-spa'). Unshelled: intercepted, no document fetch, JS state kept. Shelled: GET /navapi?p=2 fetched as a document, heading 'NavAPI page 2' without '(SPA)', and the window marker gone.
- **what_works: 'beforeunload prompts ... work' (measured with src frames).**: In the transplant flow, a link click on a page with an unsaved-changes guard shows 'Leave page?' twice. WebKit asks once for the card's own navigation (before the navigate event that Margin cancels), and again for the top-level navigation Margin then starts. Choosing Stay at the first prompt is fine.  
  Evidence: Measured with real mouse clicks ('beforeunload-on-link-click'). Unshelled, Leave: 1 dialog. Shelled, Leave: 2 dialogs, then navigates. Shelled, Stay: 1 dialog.
- **risks: real-site fidelity for 'legacy encodings' is only a possible issue.**: It is a measured failure. A document.write'd card keeps the srcdoc's UTF-8 encoding, so on a Shift_JIS (or EUC-KR, GBK, windows-1251) page, form submissions and link query strings are encoded as UTF-8 and the server receives mojibake.  
  Evidence: 'legacy-encoding'. Unshelled: characterSet Shift_JIS, submitted q=%93%FA%96%7B. Shelled: characterSet UTF-8, submitted q=%E6%97%A5%E6%9C%AC, and the link href was re-encoded from %93%FA to %E6%97%A5.

### Missed problems

- Content blockers (AdGuard, 1Blocker, Wipr): element-hiding rules for the card are evaluated against 'about:srcdoc' when the srcdoc stub loads (DocumentLoader.cpp:588-600 in the r-shell copy), and document.open keeps that result. Rules whose url-filter only matches http(s) or the page's own URL stop hiding elements in the card. Measured ('contentblocker-css'): '.*' and if-domain rules still hide; '^https?://' and '^https?://[^/]*/ads' rules hid the element unshelled but left it visible (display:block) in the card.
- Text-fragment links (#:~:text=...) no longer scroll or highlight. The directive is stripped from the top URL before Margin's script runs, so location.hash is empty and nothing reaches the card. This affects Google result highlights and Safari's 'Copy Link with Highlight'. Measured: unshelled scrollY 6992, shelled 0.
- window.close() called by the page does nothing in the card. Measured: the WebView close signal fired unshelled and not shelled. This breaks 'you can close this window' OAuth, payment and app-launcher tabs that were opened from a target=_blank link; those have no opener, so they are shelled. Fix: in the MAIN-world script, forward close() to top.
- Every navigation either flashes an empty card or freezes on the old page (measured; see the refuted paint-holding claim). The plan needs a paint-hold step: keep the shell hidden until the card's CSS has loaded. That removes the flash; progressive rendering on streaming pages is still lost.
- Scroll position is lost on reload, on Back without the back-forward cache (all HTTPS no-store pages), and probably on session restore; typed form fields are lost on Back without the cache (measured). Saving __scroll at pagehide and on reload can fix scroll; there is no general fix for form state.
- Navigation-API SPAs are degraded to full reloads (measured). The fix needs MAIN-world cooperation, for example detecting intercept() or ordering Margin's listener after the page's, and is not designed.
- Pages with unsaved-changes guards ask 'Leave page?' twice (measured). The proposed synchronous click handler would avoid it for anchor clicks only, not for forms or location.assign.
- The proposed capture-phase click handler on <a href> (section 3a) must skip modified and middle clicks. Otherwise Cmd-click (new tab), Option-click (download) and Shift-click (Reading List) become same-tab navigations, because the handler runs before Safari's policy decision. This is reasoning only; the Navigation-API path itself is safe (measured).
- Legacy-encoded documents need a skip condition: characterSet must be UTF-8 at document_start, and a meta charset found later must trigger a no-shell reload (measured mojibake).
- Safari Translate: subframes are opt-in for WebKit's text-manipulation API (includeSubframes, added in macOS 14, default NO; WebPage.cpp:9934-9945, _WKTextManipulationConfiguration.h:35). If Safari doesn't set it, only the shell gets translated. Its language detection may also read the shell's sidebar text. Unverified.
- Only title, icon, theme-color and color-scheme are mirrored. <link rel=manifest>, OpenSearch (Quick Website Search) and other head metadata that File > Add to Dock and similar features read from the top document are lost. Unverified.
- File > Save As (Web Archive): LegacyWebArchive::create(LocalFrame&) archives each frame's raw main resource (src/LegacyWebArchive.cpp:526-555). The card's is the srcdoc stub, and the page's subresources were loaded by the card, not the top document, so saved archives are probably incomplete. Source reading only.
- Toggling Keep open (Option-S) on a page loaded in auto-hide leaves today's push mode, with its fixed-element and 100vw problems, until the next navigation or a reload. Arc users toggle the sidebar constantly, so they keep meeting the push layout (fixed-element and 100vw breakage) the shell was built to replace. Always shelling, with a full-width card in auto-hide, would make the toggle seamless, but it would expose every user to the shell's losses.

### Confirmed

- Other extensions' top-frame-only content scripts land in the shell, which has no page content. Measured ('other-extension-scripts'): top-frame scripts at document_start and document_end ran with shell=true and h1=false. Scripts injected into all frames also reach the transplanted card at document_end (h1=true), so all_frames password managers keep working; they also run in the shell and the about:srcdoc stub.
- Cmd-click (new tab) keeps working on the Navigation-API path. WebKit dispatches the cross-document navigate event only after the browser's policy decision (FrameLoader.cpp:1869-1876 and 4520-4523), so a click Safari turns into a new tab never reaches Margin. Measured: ctrl-click was ignored by policy, no navigate event fired, and the top stayed on page A in both modes.
- Autofocus and typing reach the card after frame.contentWindow.focus(). Measured: active element 'q', typed value 'ab' in both modes.
- Plain fragment URLs (#id) scroll correctly after the transplant via location.replace. Measured: the target was at the top of the viewport.
- Each navigation makes one document request, and an in-card POST login is resubmitted top-level once with its body intact. Measured: one POST /dologin with username=alice&password=s3cret.
- Margin's re-issued top-level navigation is a script navigation without a user gesture. Measured policy: navigation type 'other', is_user_gesture false; native: 'link-clicked', true. So Safari's Cocoa 'skip on Back' rule depends only on the 10-second activation fallback (Document.cpp:9994-10005; HistoryController.cpp:574-585, 1102-1104). This matches the recommendation's 'likely, must measure on Safari'; my activation probe was confounded by evaluate_javascript forcing a user gesture.
- Find-in-page, notifications, element fullscreen covering the whole window, downloads, clipboard and popups opened from clicks behave like top-level pages (r-parity/out/results.txt, measured with src frames).
- Reader, Hide Distracting Items, top-only extensions and menu-bar Print are degraded, as the recommendation says.

## verify:engine: overall **sound-with-fixes**

The relayed user message 'why did you stop it' has no context in this step, so it is not answered here; this step only verified the recommendation. The core engine premises hold: Safari's DNR cannot rewrite response headers, document_start runs synchronously when <html> is created (from source), the srcdoc card ignores the page's frame-src, frame-ancestors and X-Frame-Options, Trusted Types do not block the isolated-world writer, and the Navigation API lets Margin cancel same-origin navigations. The prototype and design still have real fidelity bugs. Easy fixes: defer the write by one task (otherwise load and onload are lost); reuse the page's doctype; skip non-UTF-8 pages; use a bubble-phase click path that respects defaultPrevented. Not fixable inside the design: cross-origin target=_parent and parent.location are blocked; WebKit's third-party redirect blocking stops page top.location calls; beforeunload prompts twice unless a MAIN-world shim is added. Also unresolved: extension injection order makes the skip condition flaky, and Navigation-API SPAs break. Evidence scripts and outputs are in artifacts/v-engine/ (server.mjs, run.py, click.py, probe_tt.py, order.py, shell5v.js, base.jsonl, shell-fj0.jsonl, shell-fj1.jsonl); WebKit main sources are in v-engine/src/. All tests ran in WebKitGTK 2.52, not real Safari. XTest clicks were flaky; only clicks confirmed by a beacon or a navigation were counted.

### Refuted or corrected

- **Step 2(d) and the prototype synth/shell5.js: wait for the srcdoc frame's load, then d.open/write/close, and 'scripts run in their normal order' (page lifecycle is preserved).**: When the write runs straight after awaiting the srcdoc frame's load event, the card's window load event never fires, so window.onload and addEventListener('load') handlers never run. pageshow does fire, because the srcdoc's own unfinished load sequence dispatches it. This happens even when the card still has a pending image. Deferring the write by one task (setTimeout 0) brings load and onload back, but then the initial pageshow is missing. The synth runs show the same bug: out-pc0.jsonl and out-pc1.jsonl contain no 'frame-load' message at all, even though shell5.js listens for it. Likely cause (from source, not proven): the await continuation runs inside the srcdoc's implicitClose, and Document::implicitClose skips the load event while m_processingLoadEvent is set.  
  Evidence: Measured with v-engine/run.py and /onload?img=0|1. Unshelled: 'dcl,onload,load,pageshow'. Shelled with shell5 as written: 'dcl,pageshow' for both pages. Shelled with DEFER=1: 'dcl,onload,load'. Source: Document.cpp:4478 `doload = !parsing() && m_parser && !m_processingLoadEvent && ...`; FrameLoader.cpp:706-709 (didExplicitOpen resets m_didCallImplicitClose).
- **Serialize '<!doctype html><html'+attrs+'>' + getHTML, and the card is laid out exactly like the page in a narrower window.**: The hard-coded <!doctype html> forces standards mode. Pages with no doctype (quirks mode) or a legacy doctype (limited-quirks) render differently in the card. The original doctype node is still attached to the top document and should be reused.  
  Evidence: v-engine /quirks: unshelled compatMode BackCompat, 50%-height div 300px, image table cell 22px. Shelled: CSS1Compat, div 20px, cell 26px. /limquirks: cell 22px unshelled vs 26px shelled. WebKit main Document::implicitOpen sets NoQuirksMode, and the written doctype decides the mode.
- **Card pages behave like the original document (implied by 'one document request, correct Sec-Fetch/Referer' and the fidelity claims).**: The card is a srcdoc document, so it is always UTF-8. On legacy-encoded pages, link URLs and GET form submissions are percent-encoded as UTF-8 instead of the page's charset, so the server receives different bytes. This applies to windows-1251, Shift_JIS, GBK and similar encodings, whether the charset comes from the HTTP header or only from <meta>. document.characterSet is already correct at document_start (measured 'windows-1251' at takeover), so a cheap skip condition is possible.  
  Evidence: v-engine/run.py enc, enc_form, enc_link, enc2, enc2_link. Unshelled: characterSet windows-1251 and query q=%EF%F0%E8%E2%E5%F2. Shelled: characterSet UTF-8 and q=%D0%BF%D1%80%D0%B8%D0%B2%D0%B5%D1%82 (server log), for both header-declared and meta-only charsets.
- **Step 3(a): also add a capture-phase click handler on <a href> that performs the same top-level navigation synchronously inside the user gesture.**: A capture-phase handler runs before the page's own click handlers. Client-side routers (React Router or Next.js Link style: preventDefault plus pushState) therefore lose every link, and each click becomes a full top-level page load. Routing through the navigate event alone keeps the SPA working. If a click path is wanted, it must run in the bubble phase on window and respect e.defaultPrevented.  
  Evidence: Real XTest clicks with v-engine/click.py on /spalink. Unshelled: final /spalink?view=2, 1 document request. Shelled with navigate-event routing only: /spalink?view=2 (the MAIN-world wrapper works). Shelled with the capture handler (CLICK=1): final /dest?from=spalink, plus a second document request.
- **Every cross-document navigation inside the card is cancelled with the Navigation API and redone as a top-level navigation; 'Let every other top navigation through'.**: WebKit fires the cross-document navigate event only when the requester can access the card's document. Navigations requested by cross-origin documents never reach Margin. Worse, WebKit refuses to let a cross-origin child navigate a parent that is not top. So target=_parent links and parent.location assignments in cross-origin iframes inside the card silently do nothing, while unshelled (where parent is top) they navigate the tab.  
  Evidence: FrameLoader.cpp:1867 (requesterCanAccessDocument gate) and FrameLoader.cpp:3974 (same-origin gate). Document.cpp canNavigateInternal, ending at 5378 ('neither same-origin with the target, nor is it the target's parent or opener'). Measured: /xoparent?how=assign navigates unshelled and does nothing shelled. Real-click /xoparent?how=manual (cross-site iframe, target=_parent link): unshelled navigated to /dest on every landed click (4 runs); shelled, the click was delivered (beacon child-clicked&ua=true) but no navigation and no request, on every landed click (4 runs).
- **Page-initiated top navigations are fine because 'top-level is the correct place for navigations'.**: Page code in the card that calls window.top.location = <cross-site URL> without any prior interaction with the card is blocked by WebKit's third-party iframe redirect blocking whenever the card has loaded a third-party script and a third-party frame, which is very common with ads and analytics. Unshelled, the same code is a self-navigation and is never blocked.  
  Evidence: Document.cpp:5393 isNavigationBlockedByThirdPartyIFrameRedirectBlocking (isUntrustedIframe = hasLoadedThirdPartyScript && hasLoadedThirdPartyFrame). Measured /topnav (3P script + 3P iframe, then top.location to 127.0.0.1): unshelled navigated, shelled stayed on /topnav with no request. A same-site destination (/topnav?same=1) passed.
- **what_works: beforeunload prompts work.**: Following a link in a card page that has a beforeunload handler shows the prompt twice. In this load path WebKit runs shouldClose (beforeunload) before the pending navigate event, and the shell's top-level navigation then runs beforeunload again on all descendants, including the card.  
  Evidence: FrameLoader.cpp:4450 (shouldClose) runs before FrameLoader.cpp:4520 (pending navigate dispatch). Measured /bu with a real click: unshelled 1 BEFORE_UNLOAD_CONFIRM dialog and 1 beforeunload beacon (5/5 landed clicks); shelled 2 dialogs and 2 beacons (4/4 landed clicks).

### Missed problems

- Content scripts from different extensions run in an arbitrary order. WebUserContentController::forEachUserScript iterates a HashMap keyed by content world (WebUserContentController.h:130, .cpp:678-686). A document_start script from another extension that inserts a <style> into <html> (Dark Reader style) can run first, and then the 'already has children' skip condition sends the page to push mode. Measured with v-engine/order.py: worlds 'darkreader' and 'ext3' added first made Margin skip (kids=1); 'adguard' added first did not. When Margin runs first, the other extension's nodes end up in the shell head instead of the page. So go/no-go step 1 can pass in a clean profile and fail for real users. The skip test should look for parser-created head/body, not any child.
- Navigation-API SPAs break whichever way the listeners are ordered. If the page's navigate listener runs first, its intercept() is then cancelled by Margin's preventDefault; if Margin runs first, intercept() is no longer possible. Measured /navspa: unshelled stays SPA ('view 2 (spa)', 1 request); shelled does a full document load of /navspa?view=2 with FRAMEJS 0 and 1.
- The cross-document navigate event in WebKit is dispatched after the UI-process policy decision (FrameLoader.cpp:1867-1876 pending dispatch, 4520), outside the click's gesture. A real click gave e.userInitiated=false for cross-document navigations but true for same-document ones. So the shell's location.assign never carries processingUserGesture, and avoiding the Cocoa Back-skip rests only on the 10 s activation window. Safari's policy delegate also sees a subframe navigation before Margin can cancel it.
- The main-world history wrapper is not idempotent. Any later document.open on the card document (including a page rewriting itself) re-runs document_start scripts on the same Window (HTMLConstructionSite.cpp:327-333), which wraps History.prototype twice. It needs a guard. This is from source reading only, not measured.
- Overstatement: if the go/no-go fails, the fetch-and-write variant (alternative 3) can still give a true viewport on many sites, at the costs listed. So 'no extension-only way' is too strong.

### Confirmed

- Safari DNR never applies responseHeaders. In WebKit main, ModifyHeadersAction::applyToRequest (ContentExtensionActions.h:110,139; .cpp:163-167) only iterates requestHeaders. responseHeaders is only parsed and serialized (.cpp:100-155). BCD lists RuleAction.responseHeaders as Safari false. So DNR ordering against XFO and CSP enforcement does not matter.
- document_start injection is synchronous at parser creation of <html>, before any child exists: HTMLConstructionSite.cpp:327-345 calls LocalFrame::injectUserScripts (LocalFrame.cpp:793-861). WebExtensionContext.cpp builds content scripts as plain WebCore::UserScript with the manifest injectionTime. UserScript.h in main has no wait-for-notification field, so there is no source-level deferral path. Real Safari timing is still unverified.
- Re-injection into the document.write'd <html> is not gated on script-created parsers (dispatchDocumentElementAvailableIfNeeded only checks m_isParsingFragment). Measured: frame-cs runs in every transplanted card.
- The srcdoc card is not subject to the page's frame-src, child-src or default-src. With frame-src 'none', child-src 'none', or default-src 'self' plus a nonce script-src, the card rendered, the nonce script ran, and there was 1 document request (v-engine fsrc_* runs).
- An X-Frame-Options DENY plus frame-ancestors 'none' page (/dest) renders in the card after a top-level navigation, from a single document request (enc_link, meta and xo_top runs).
- Cross-document, non-traverse navigate events are always cancelable (Navigation.cpp:1467). Link clicks, form GET, form submit() and meta refresh in the card were all routed to the top as one top-level request each (meta: /dest?from=meta).
- Trusted Types do not block the isolated-world writer in WebKit. On require-trusted-types-for 'script' pages, including trusted-types 'none', the isolated world's document.write and innerHTML into the card succeeded, while the same calls from the main world threw TypeError (v-engine/probe_tt.py). Only the Chrome MAIN-world writer is TT-sensitive.
- Safari 27 change 173369038 is low risk. Main's Document::open now only checks same-origin and sets URL and cookieURL. It strips the fragment when entryDocument != this (Document.cpp:4254), which explains the lost hash. srcdoc still aliases the owner's SecurityOriginPolicy (Document.cpp:8842-8844), so document.domain in the card is harmless: measured /ddomain shelled, pushState ok and parent access ok.
- Back/forward with the page cache works: synth/out-pc1.jsonl traversals made 0 requests. Child-frame history restore is keyed by uniqueName (FrameLoader.cpp:1253), so the random frame name is effective while UseUIProcessForBackForwardItemLoading stays off (UnifiedWebPreferences.yaml, default false, unstable).
- Cocoa back-forward skip rule reading is correct: HistoryController.cpp:574-585, Document.cpp:9994-10005 (10 s window), LocalDOMWindow.cpp:1731-1742 (activation copied to ancestors).
- SPA pushState through the MAIN-world top-owned history wrapper works (spalink without the click handler: top URL /spalink?view=2, no extra request).
- Release notes: Navigation API in 26.2 (158642673), Trusted Types in 26 (130065736), registerContentScripts excludeMatches fix in 26 (145489255), match_about_blank in 18.4 (145875291), getHTML shadow roots in 18 (125513986).
- ENABLE_WK_WEB_EXTENSIONS_SIDEBAR is 0 in open-source PlatformEnableCocoa.h:1115-1117. It is guarded by #if !defined, so an Apple-internal build could override it; shipping Safari is unknown.
