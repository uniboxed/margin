# WebKit host

A small stand-in for Safari, for testing Margin on Safari's own extension engine without opening or automating Safari.

It is a macOS command-line program (`host.swift`) built on WebKit's `WKWebView` (the page engine) and `WKWebExtensionController` (the extension engine Safari uses: content scripts, the background page, `browser.*` APIs, registered scripts, native messaging). It loads Margin's Safari build (`dist/webkit`) into one window with a few tabs, plays a scenario (open tabs, install or update Margin, switch tabs, put a tab to sleep, run JavaScript in a page, take a screenshot), and checks the results. The window is off screen (at −20000, −20000, ordered in behind everything) and the program never becomes the active app, so nothing appears while it runs. AppKit moves a titled window onto a screen as it's ordered in, so the host's window keeps its place by overriding `constrainFrameRect(_:to:)` (until 2026-11-06 it showed at the top left of the main display during every run).

## Running it

```sh
npm run build                         # the host tests dist/webkit (the Safari build)
tools/webkit-host/run.sh all          # every scenario; exits 1 if a check failed
tools/webkit-host/run.sh switching    # one scenario
npm run test:webkit                   # the same as `run.sh all`
```

Needs macOS with Xcode's command-line tools (`swiftc`) and Node. `run.sh` compiles the host into `build/` when `host.swift` changes, copies `dist/webkit` to `build/ext` with a small hook (`hook.js`) that sends Margin's console output to the test server, starts the server (`server.mts`, port 47811, serving the test pages), runs the scenario and prints both logs: the host's steps with each check's `PASS`/`FAIL`, then Margin's console.

## Scenarios

Benchmarks are run by name, not by `run.sh all`: `box-bench` (the box's cost on heavy pages, plain and boxed: `npm run bench:box` runs it beside Chromium's and reads its `BENCH` lines).

In `scenarios.mts`, each a list of steps (documented at the top of the file). A check (`check` in Margin's content-script world, `checkPage` in the page's) waits until its JavaScript returns `true`, up to a timeout, so scenarios don't depend on fixed waits.

## Real websites

`open` also takes a full URL (`https://…`). The host logs every navigation (`nav <tab> top go <url>`, `committed`, `loaded`), so redirects and reload loops show. Each page's own console errors, warnings, uncaught errors and CSP violations are kept in `window.__pageLog` (read with a `page` step); Margin's log lines in the content-script world in `globalThis.__marginLog` (a `check`/`eval` step), since a site's CSP can block sending them to the server. Run a one-off scenario file with `./run.sh path/to/scenario.json`. Several runs can go at once with their own `MARGIN_HOST_PORT` and `MARGIN_HOST_BUILD` (a folder); `MARGIN_HOST_TIMEOUT` sets the time limit in seconds. The host has no signed-in accounts.

## Limits

- It isn't Safari. Everything around the engine is this program's: tabs, the window, sleeping tabs, launching and relaunching. That's where it can differ from Safari (it once loaded a hidden tab on `tabs.reload`, which Safari never does), so confirm tab and window behavior in Safari's own log (`/usr/bin/log show`, passively) or in Safari itself.
- Where it follows Safari on purpose (2026-10-29): `tabs.reload` leaves a tab asleep alone; a tab asleep is shown Safari's way, its web view into the window before it has a process and its load 30 ms later (Safari restores it after its session storage is back), so WebKit doesn't count that first moment in the window; selecting a tab takes 2 ms of the main thread (Safari's own selection turn lasts 2–74 ms in its log), so a second tab change sent with the first lands in the same run loop turn, as in Safari; the `deferLoads` step loads a tab asleep only if it's still the one shown once the turn is over (Safari can put a selected tab's load off until its selection update is done), and makes its web view as it's selected all the same, as Safari does (a script there then gets an error in place of a result, rather than failing). A web page's tab put to sleep (`sleep`, `restart`) loads again from its saved history (`WKWebView.interactionState`), as Safari restores one (`restoreFromSessionState`, then `goToBackForwardItem`, with no process yet, in Safari's log of 2026-11-02): its page's navigation is `back_forward`, as in Safari.
- What the app's end heard (link-server's `ev` lines: a push with its message, a reply) is kept for checks: `appMark`, then `appHeard { has, re?, none? }`. `appReq { type, payload | in, js }` sends a request from the app's UI for the copy's first window (link-server reads it on stdin), and its reply is heard.
- Native messaging goes to `link-server/` (Margin.app's own link code, built by `run.sh` with the app's flags) when an `appStart` step has started it (`layout`: the page slot's insets it reports, 300/40/20/24 by default; `appLayout`: new ones, as the overlay measuring again; `appDrawn`: whether it draws over that window, as the shell says when a window is bound or isn't; `appQuit`: it says goodbye; `appLoseAnswers { count }`: the next wantLinks are passed on to it but never answered; `appKill`: it's killed; `appPings`: the copy's pings on its port so far); otherwise the host answers as Safari's handler does with no app running, or, after `appOnDemand`, starts it at the next wantLink and answers `launching`, as the handler does. It plays only the app's link: no overlays, no window tracking, so what the app draws isn't seen here (pages draw nothing of Margin's since Margin 2 Phase 2 step 5: `tools/app-tests` covers the overlay).
- Registered scripts dropped (`scripting.unregisterContentScripts`) still run in web views made after they were registered, until the host restarts (seen for the first-paint placeholder and the page's script after the link went off, Phase 2 step 5). Tabs open before the registration are clean. And one registered again after another came in between loses to that one, where an update's newest files win: so Margin only updates its first-paint registration once it has made one (DECISIONS.md, Margin 2 Phase 3). Whether Safari does the same isn't known.
- Margin's background was a service worker until Margin 2 Phase 2 step 3a; it's a page now (`bg-page`: alive 22 s after install). As a worker it stopped about 5 s after it started, whatever the build, and nothing starts it again: every message after that gets an empty answer (`browser.runtime.sendMessage` resolves to undefined at once). Neither page messages nor tab events keep it running, and `loadBackgroundContent` takes it as still loaded. Safari keeps it running while it's needed and wakes it for a message. So a scenario does what needs the background within about 4 s of `install` (or splits into several scenarios); a step later than that fails, at random near the edge. On 2026-11-02, with the Mac busy (load average 7–20), it often stalled from about 1 s after it started, timers and all (a heartbeat every 100 ms in it stopped for 2–4 s), on this build and on HEAD's alike: `tabids` failed on both. A scenario whose switch lands well past that is flaky then. To check, send 30 × `getZoom` from a page and look for `undefined`. The background page's WebContent process runs at background priority (`ps -o pri`: 4, a shown page's about 47), as WebKit runs a process that shows no page: its timers fire in wakes about 250 ms apart, a message on its socket waits for one of them, and with the Mac busy it can get no time for seconds (Margin.app's `drawn` read 2 s after the link server sent it, 2026-11-06).
- A tab's web view is made again when `tabs.update` takes it between a web page and an extension page, or from a copy's pages to another's (its configuration belongs to one), as Safari's tabs go anywhere. The new web view has a history of its own (what Safari does with a tab's history then isn't known). An extension page's web view the tab leaves is kept, out of the window: closing one stopped Margin's background for good here (2026-11-04). WebKit refuses a web page's own navigation to an extension page (−1008) and never commits an extension page's own navigation to a web page: both go through `tabs.update`. The host keeps its pages visible as Safari's on-screen window does: its web views ignore the window server's occlusion (WebKit's private `_setWindowOcclusionDetectionEnabled:` set to false; an off-screen window is marked occluded, and a tab that was shown then stayed `document.hidden`), and App Nap is off for the run (an accessory app with only an off-screen window is napped after a minute or so). A tab hidden is its web view out of the window, which WebKit counts hidden whatever the occlusion. Key and mouse events don't go through the window server: the `key`, `mouse` and `pinch` steps hand them to the web view itself, so where the window is doesn't change them. A pinch's magnify events have no window, and WebKit takes their screen point as a point in the window, so `pinch` gives its `x`, `y` as one (it added the window's origin until 2026-11-06, which only worked with the window near the screen's corner: off screen, the gesture missed the page).
- Memory: a page that navigates from a `page` step (the host's `callAsyncJavaScript`) stays in memory when any content-script world is in the page, even an empty one, so footprints measured that way grow with every navigation whatever Margin does. Let the page navigate itself (a link, its own script) to measure memory. `heap <pid>` and `vmmap --summary <pid>` work on the host's web content processes and count what's kept (`WebCore::HTMLDocument`, `WebKit::WebExtensionAPINamespace`: one per page kept).
- No real trackpad: the `pinch` step sends real magnify events, but how gestures feel, and pull-to-refresh, aren't covered here. Off-screen snapshots can't show whether text is sharp.
- The engine is the one in the installed macOS, which may be newer or older than a user's Safari.
